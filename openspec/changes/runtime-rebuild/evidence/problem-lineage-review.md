# 问题脉络与需求本质（历史版本问题反馈邮件分析，2026-10-18）

> 定位：只看问题，不为复活任何设计。**部分问题正是设计导致的**——每题穿透到"设计致病点"，再提炼需求本质。判据：穿透行为看本质，过往契约不作金标准。
> 信息边界：正文细读 5 封（10-14 结算回流/10-13 TTL 收割/10-09 血统扣留/09-27 跨 session 串场/09-30 tmux 双断连）；标题级覆盖收件箱全量 54 封（P6-P10 由标题与摘要定性，未读全文——成色标注⚠️）。

## 一、问题清单（现象→设计致病点）

| # | 现象 | 设计致病点（根因定性） |
|---|---|---|
| P1 | 后台任务完成但结算不回流 agent 语境，挂到 TTL 才以 failed 暴露；看板补发延迟分钟-小时级；同回合并行任务正常、唯个别丢失 | **推送模型**：结算=事件注入（fire-and-forget 投事件流），非账本登记。"注入时机×回合忙闲"竞争必然产生丢唤醒窗——状态成了投递的副产品 |

| P5 | tmux -d 长作业三次失败零结算零唤醒；四层机制（emitBackground/alive_detached/stale/task_job_deadline）全部无米下锅 | **拓扑耦合**：托管=进程树+输出管道的隐式拓扑。tmux -d 脱管 fork 两头断——所有权寄托于"谁是谁的孩子"而非显式登记 |
| P6 | email-inbound 轮产出被 delivery-gate 静默消化，用户状态同步丢失 | **静默分支**：gate 存在"消化"这个无回执出口。拒绝不具名=丢失不可审计 |

| P8 | 压缩风暴（24h 回收率衰减 1-4.5%）/摘要超时（5s 误配） | **压缩启发式当保留语义**：历史保留没有"必须留什么"的显式策略，靠摘要/压缩省空间——超时参数与压缩回收互相踩 |
| P9 | task-batch-retire 扣留二连、meditation 分支扣留《最近比较烦》交付（感知成功/发送未发生） | 同 P3 族：白名单+血统推导模型的必然产物（扣留是设计行为，不是 bug） |
| P10 | :80 回归事故＋PARTIAL 告警伴生（09-16） | 门禁缺口族（⚠️ 标题级）：变更与验证的耦合面失控 |

## 二、脉络：三类设计病（共根）

```
推送模型病（P1 P7 P9）        代理指标病（P2 P5 P8）        派生值病（P3 P6 P4）
状态靠投递传播                 语义靠可观测代理              不变量靠运行时推导
  ↓ 丢唤醒/错触发/扣留          ↓ 误判死/断连/误删            ↓ 污染/静默丢/串场
───────────────────────────────────────────────────────────────
共根：把"该登记的事实"做成了"该推导的过程"
```

- **推送模型病**：状态本应是随时可读的事实（读即真），设计里成了事件投递的副产品——投递丢窗口、唤醒条件挂错、扣留白名单都由此生。
- **代理指标病**：用可观测的代理信号（输出节奏/进程父子/压缩率）代替语义事实（工作活性/所有权/保留需求）——代理与真值错位时，机制全部"无米下锅"（P5 的四层机制健全但前提缺席）。
- **派生值病**：受理/登记时就该定格的不变量（血统/交付资格/隔离边界），被做成运行时从上下文推导——推导源被污染则全链错（P3 的"回合血统跟着批次事件走"）。

## 三、需求本质（正向陈述，不指向具体实现）

| # | 需求本质 | 消灭的问题 |
|---|---|---|
| R1 | **任务状态=一等账本事实**：完成/失败是任务自身的状态转移，任何时刻读任务即读真值，不依赖通知送达 | P1 |
| R2 | **活性=工作语义**：活着=承诺在推进（进程/工作事实），死亡=显式裁决（谁判/何时判/判据是工作承诺而非输出节奏）；收割与结算是同一条账 | P2 |
| R3 | **交付资格=受理时登记的不变量**：来源/授权/血统在受理一刻定格为事实，运行时只读不推导 | P3 P9 |
| R4 | **隔离=第一性边界**：现场即隔离单元，读取按现场边界取数，不存在"共享池+过滤"形态 | P4 |
| R5 | **执行承诺=显式登记**：谁在等什么、等不到时谁裁决、裁决路径是什么——不寄托于进程树/管道拓扑 | P5 |
| R6 | **拒绝=具名回执**：任何投递/交付的拒绝必须具名、可审计；不存在静默消化分支 | P6 |
| R7 | **触发=事件/事实驱动**：不从否定性状态（"空闲""无事"）推断触发条件 | P7 |
| R8 | **保留=显式策略**：必须留什么由业务声明；压缩/摘要是实现细节，不承担保留语义 | P8 |

## 四、判读

1. 十个问题不是十个 bug，是**三类设计病在十个表面的发作**。逐个修表症（补唤醒/调 TTL/改白名单）会复发——邮件时间线显示同族问题跨 09-16→10-14 反复出现（扣留族至少 4 次、结算族至少 3 次）即为实证。
2. P10 与其余不同族（门禁耦合），单独跟踪。
3. R1-R8 是验收判据级的陈述（可反事实检验："若违反此条，P 系列哪个会复发"）；不指向任何具体实现形态。

## 五、prototype 对照反思（问题变少/出了问题更好修）

| 问题 | prototype 的形态 | 反思结论 |
|---|---|---|
| P1 结算回流 | task_manager："通知一律经 owner.Publish 投回所属管线（单点关系）"——**同样是推送模型**，但任务表在 AgentState 内可读（账本属性潜伏）；无 TTL=无假失败症状 | 原型症状少（无 TTL 假死）但丢唤醒根病同在。**账本可读（任务表）比通知送达更本质**——原型有一半，被 Publish 模型掩盖 |
| P2 TTL 收割 | **无 TTL/quiet_timeout**（task_manager 明示未实现）——问题不存在 | **机制制造问题类**：杀超时是后加的，"活性判死"裁决面没有语义定义就必然发病。第一定律：引入机制前先审它制造什么问题类 |
| P3 血统扣留 | **无 delivery-gate/白名单**（Deliver 直接回流）——问题不存在 | 同上：治理面把"不确定就扣"当默认，制造了整族问题（P3/P9 四次复发） |
| P4 跨 session 串场 | AgentState 按 agent id **现场自持**（队列/上下文/Memory per 现场）——天然隔离 | 共享池+事后过滤是后来的共享化改造引入的退化。**现场自持=隔离第一性**的原型朴素形态是对的 |
| P5 tmux 双断连 | 任务=登记+可取消 ctx（语义边界），不假装托管 | ctx 也不知道 tmux 里 python 死了（根病同在），但原型**不假装有保护**——问题早暴露。现树四层机制"健全但前提缺席"的形态更危险 |
| P6/P7/P8 | 无 gate/idle gate/压缩启发式——问题均不存在 | 同 P2/P3：机制引入史=问题引入史 |

**"问题变少"的第一定律**：P2/P3/P6/P7/P8/P9 六题全部是**后加机制制造的**——原型简单面天然没有。每引入一个机制（TTL/gate/idle/压缩/白名单），先反事实审"它制造什么问题类"。
**"出了问题更好修"的三要素**：账本可读（问题挂哪可查）＋具名回执（丢失可审计）＋显式裁决路径（谁判/何时判可复盘）——原型缺第三件，现树的诊断面（Query/Diagnostics）是补位。
