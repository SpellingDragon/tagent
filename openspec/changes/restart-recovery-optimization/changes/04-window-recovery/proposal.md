# 04-window-recovery 提案

## Why

两条实测事实把范围顶到这里：

1. **锚 A 的红不在恢复机制**：同一代 boot 里票据装载 2.8ms、restore-chains 0.005ms，而启动期读侧重建（观察表全量 land、`landedSeq` 全量扫、回放投影全量折、向量缝全量 Submit）占 16.8s（96%）。冷读平方问题已修（w256 gen7 17.5s→1.1s，判据是「24 条事件 24 次分片扫描→1 次」），但历史线性项仍在。
2. **两处概念错位**：「窗口」这一类有 17 个冻结标量（9 个配置键 + 6 个代码常量 + 2 个派生常量），互相没有派生关系；而 recall 与语义召回被错误地绑在 runtime 窗口上——它们本应只读**落盘的事件数据**。

## What Changes

### A. 窗口类界收口（压缩策略零改动）

- 唯一窗口输入：`max_tokens`。
- 删配置键 7 个：`provider_context_window`、`output_reserve`、`long_context_tokens`、`capture_budget_mb`、`vector_top_k`、`keyword_top_k`、`rrf_k`。
- 删代码冻结石：`factWindow`(2048)、`replayResidentWindow`(2304)。
- 派生/降常量：provider 窗=回放窗；输出余量=窗/4；`long_context` 降为策略（值由装配剩余量算出）；捕获与缓存预算=窗口渲染字节×固定倍数；检索页界一个数；RRF K=60；`BudgetCharsPerToken=4` 唯一换算常量。
- 常驻界派生：内存里的投影与事实=窗口渲染集。
- 配置、schema 白名单、reload 语义、示例配置与全部关联文档同批改；旧键出现→具名拒绝。

### B. recall 与 runtime 窗口解耦

- 召回与查询只读**落盘的事件数据**，与 runtime 窗口无关。
- 观察表退役为**查询缓存**：启动零 land；查询按自己的过滤条件从持久层读、分页；缓存可丢、不是真源。
- 不设「无界查询拒绝」：召回本就是找持久历史，成本由分页/limit 与查询范围决定。
- 语义召回：内存不保留 runtime 窗口的向量状态，也不建全史向量表；查询时对本次候选集现场算向量（可加 LRU）；启动零向量工作。

### C. 窗口内重建

- 投影：启动只折窗口内的段，再挂链上已有产物；窗口起点=产物覆盖边界+最近未闭合段（链上算得）。
- `landedSeq`：读段索引尾，不读正文。
- tier 打开：分片校验改懒校验。
- 验收：窗口内重建出的投影 ≡「全量折叠后裁窗」逐条一致；启动的 `EachEvent` 条数=窗口条数。

## 边界与依赖

- 依赖：03（票据/快照纪律与失败退回内核）已放行。
- **压缩策略零改动**：段处理、`keep_recent_tasks` 开关、分龄推断、阈值、提交后判卷、判断事实与产物事实、替换语义、两个策略默认值——一行不改。
- 不落第二真源；不改事件契约、事实族、插件 f(x) 管线、交付/冥想语义。
