## 一 A 复核：结论＝内容确定性，非放宽

### 1.1 断言面（未放宽）

### 1.2 机理链（代码实证，逐条可点）

1. 事实的 window 就是毫秒：`assembly/facts.go:498` `window := evt.Timestamp.UnixMilli()`；`assembly/run.go:3402` `WindowTS: timestamp`。
2. 一个 `(partition, window)` 一个 meta 键：`memory/ledger/segment_store.go:1392` `windowMetaKey`；`segment_store.go:1365` `nextWindowMeta` 在同窗口累加同一键（两条事实同毫秒⇒共享一个键）。
3. boot 按地址读一条事实即读一次它窗口的 meta：`segment_store.go:547` `publishedPosition` ← `:529` `partitionPositionLocked`（每次 `GetEventInPartition` 一次 index 读 + 一次 window meta 读）。
4. 同一 key 的重复读由 resident set 承接、不再计 addressed value read：`memory/ledger/journal_kv.go:286` / `:302`（`k.resident.get` 命中即返回，不调 `log.addr.value`，故 `valueReads` 不增）。

⇒ 两条墙钟事实落进同一毫秒，其后 boot 少读 1 个 value。这是 ±1 的唯一来源。

### 1.5 残余风险（本单未消除，交编排者裁；下一轮 CI 若报 gen≥2 的 ±1 即此因）

- `awaitNextStamp` 只分隔**步骤**，不分隔**一次调用内部**落的多条墙钟事实。commit 步骤里压缩折叠各自 `time.Now()` 落 request/product（`assembly/compress_consumer.go:616`），本机 dump 显示每个 commit 步骤内 2 对、对内间隔 ~5ms。
- 机速折算（同一条 252 代长跑行走，本机 vs CI `test (short)` 作业中位数）：commit 步骤 34.3ms vs 6.4ms，boot 7.0ms vs 12.2ms ⇒ commit 侧约 5.4×。对内 5ms 折算 ≈0.9ms，正落在毫秒边界附近：两棵同形树的每一次"这对事实是否跨毫秒"近乎独立掷币，22 代 ×2 对的合并次数几乎必然不相等，故 gen≥2 的 ±1 仍可能出现。
- 本机复现不出（对内间隔 5ms 稳定跨毫秒，合并数恒为 0）；CI 的快机上目前只在 gen 1 被观测到过（那一次是三条 checkpoint 事实同毫秒）。
