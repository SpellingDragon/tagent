## 一 覆盖分离的形态

**一句结论**：投影 cut 只界定投影自己的重建；压缩账户的读取边界由压缩账户按自己的切片自述（`RestoreCoverage`），协调者既不读其载荷、也不按压缩事实修正投影。

| 契约要素 | 落点 | 形态 |
|---|---|---|
| 自述声明面 | `assembly/checkpoint.go:874-895`（`coverageRestore`） | 与 `restoreSeat` 同形：拥有者在自己的装配处追加（`compress_mount.go:30`），协调者只按声明顺序调用（`restoreCoverageState`，`checkpoint.go:887-895`） |
| 自述读取 | `assembly/compress_checkpoint.go:198-215`（`compressStateSlice.RestoreCoverage`） | 用 `s.StateName()` 取自己的切片：cut 在册 → 不读（该切片在 quiet point 读，覆盖重建边界以内）；cut 缺片 → 读全链压缩事实 |
| 读取实现 | `compress_checkpoint.go:217-249`（`readCompressionHistory`） | 索引先走后读身：只读 `event.CompressionMechanism` 类型，按 commit order 升序折叠，投影素材一次不读 |
| 缺片读的入口 | `assembly/run.go:1098-1130`（`restoreCheckpointState`） | 只在"框架切已恢复"的 boot 跑；`restoreNewestCheckpoint` → `restoreSessionCheckpoints` → `restoreCoverageState`。顺序是硬约束：`restoreCompressSlice` 会**替换**该 session 的欠账批，读在它之前会被覆盖 |
| 协调者去特判 | `assembly/run.go:3030-3068`（`replayChainPastCut`） | 删 `compressCut`/`seamBoundary` 形参与 `behind` 分支；函数只剩"边界以上整条重放" |

**为什么删 `behind` 是行为等价**（反事实，不用"省一次读取"作理由）：`behind` 读的是 `(compressCut, survivorBoundary]` 的压缩事实交给压缩账户。框架切的切片与投影 survivor 在**同一个 quiet point** 读（`Checkpoint` 契约：`MUST read the watermark before the state`，快照晚于 cut 读），因此该区间的每个压缩事实在切时刻已被账户应用过、已由压缩切片自身陈述；重放它是对同身份事实的幂等重折，语义零变化。缺片时 `compressCut == nil`，`behind` 本来就不跑——audit #6 的 16 条覆盖区事实正是这样丢的。**投影边界不再替任何消费者定界**：缺片者自读（本单），有切片者由自己的切片陈述（delivery 已有 `eachFactPastCut` 自读，tasks 走 `SeatRestore` 全志兜底，均为 02 段落地的既有形态）。

`seedAnchorSurvivors` 的 `(seamBoundary, anchorBoundary]` 段折**保留**：它是"锚只界定投影呈现、只有 cut 能界定 seam 可跳区间"的通用折（`TestAnchorRebuildFoldsTheRangeNoCheckpointVouches` 以具名贡献切片钉住，`consumer.derivedOf(anchor-seam-0-3)`），不是压缩特判；删它即该锚转红，属停止条件"特判删除致行为漂移"。

**"每个事实只折一次"仍成立**：缺片读只折压缩账户、**不走 state seam**（`foldCompressionFact` 直接 `consumer.Reduce`），所以贡献切片的折计数不变——`TestRecoveryDerivesNoSecondTime`（boot 每事实恰 1 次）在本树绿（见 §三），这条是覆盖分离没有把读摊到别家消费者身上的直接证据。

## 二 D2 判定：`anchorEntry.Content` 是唯一可读来源，保留

**判定**：保留副本，不改为统一读回。依据是身份面而非成本：

- 载荷条目只带 `Key`（fold product key）、`Type`、`Summary`、`Content`、`Time`；产品事实（`compress.product`）按 `CompressProductFor(request, producer, key, …)` 的**内容寻址 ID** 落盘，`request` 不是条目字段，`producer` 是常数，所以条目携带的标识没有一个能点到该事实。
- 要读回只能扫全链产品事实去比 `compress_key`——那正是锚/切存在的理由（不读覆盖区历史）；且会引入"第二读法必须与链一致"的第二真相。
- 重新生成同样被拒：`TestCompressionAnchorLocatesEveryProducerWithoutRerunningModel` 断言 restore 期间模型请求数为 0（"a restore never mints a second summary"）。
- 映射条目（链自述文本）已经**不**带副本：`carriedTextOf` 只对 `segment-fold`/`history-summary` 返回文本，同一测试对映射条目断言 `Content == ""`（`compress_checkpoint_test.go:717-721`）。

判定写在声明处：`assembly/compress_consumer.go:391-405`（`carriedTextOf`）。

**两侧锚（既有，本单复跑绿）**：

- 正：`TestCompressionAnchorLocatesEveryProducerWithoutRerunningModel` —— 切/锚两条 restore 路径都用载荷文本复原 fold 条目，模型零请求；且被复原文本与产品事实的 `Text` 逐字相同（副本不铸第二文本）。
- 负：同测试 `requireUnstatedSurvivorRefusal`（`compress_checkpoint_test.go:905-926`）——载荷命名链上无事实且不带文本的 survivor，restore 以 `ErrCheckpointSurvivorUnstated` 具名拒绝，**不**呈现空条目；同测试另两条：缺 `compress_key`/`compress_request` 或身份与自身键不符的产品事实读回零产品。
