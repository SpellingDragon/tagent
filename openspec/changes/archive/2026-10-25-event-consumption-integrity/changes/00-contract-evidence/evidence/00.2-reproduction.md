## 三、红证一：`duplicate_notice_material`（EVID-02）

- 失败位置：`tests/integration/host/event_integrity_test.go:438`（业务断言 `len(inputFacts) != 1`）。
- 通知身份：`task-2:0:settled:0`（task `task-2`，kind `settled`）。
- 随动 invocation：`session-reproduction-duplicate#2`。
- 原文（两轮一致，仅随机事实键不同）：

```
the follow-up notice identity task-2:0:settled:0 (task task-2 kind settled) generated 2 new user-input facts
in invocation session-reproduction-duplicate#2, want exactly 1:
[key=6e6f746963650033320073657373696f6e2d726570726f64756374696f6e2d6475706c69636174652332007461736b2d323a303a736574746c65643a30
 type=feedback role=user invocation=session-reproduction-duplicate#2 task=task-2
 content="tagent: task task-2 settled\nresult:\nthe duplicate notice worker reports 42";
 key=5-<per-run-hash> type=external_input role=user invocation=session-reproduction-duplicate#2 task=
 content="tagent: task task-2 settled\nresult:\nthe duplicate notice worker reports 42"];
the follow-up decision carried 2 user copies of the material, so the same settled notice entered the model twice
```

- 事实级观测：
  - 第 1 条 `type=feedback`，key 为 `hex("notice\0"+len(inv)+"\0"+inv+"\0") + hex("task-2:0:settled:0")`，携带 `task=task-2`；
  - 第 2 条 `type=external_input`，key 为铸造键 `5-<hash>`，`task` 为空；
  - 两条正文完全相同，同属 `session-reproduction-duplicate#2`，该次决策请求内出现 **2 份**该通知正文。
- 判定口径：只按**通知身份 + 事实键 + 因果归属**判定“为该通知新生成的用户输入事实/新 invocation 输入”次数；正文在更早历史中的合法重现不计入。重试幂等键本身在链中恰 1 条（`NoticeFactKey` 未重复），缺陷是同一 invocation 内 Feedback 与 ExternalInput 各生成一条同正文输入事实。
- 红前已通过：正式交付事实恰 1（`settle_trigger_source=settled`）、通知身份可唯一还原、同正文事实同属一个 follow-up invocation。

## 四、红证二：`busy_notice_loss`（EVID-03）

- 失败位置：`tests/integration/host/event_integrity_test.go:570`（30s 观测窗内无后续消费）。
- 场景：第一个通知驱动的 follow-up 被 03.1 模型屏障 park 住，期间第二个任务终态通知到达；放行第一个 follow-up 并等待其发送后，30s 内轮询 provider 请求。
- 原文（两轮一致）：

```
the settled delivery fact settle-7461736b2d343a313a736574746c65643a30 (task task-4 kind settled)
was recorded while the first follow-up was parked at the model, but no later decision consumed it within 30s:
model requests = 7,
sender bodies = ["the first background task was accepted" "the second background task was accepted" "the first background notice reached the user"],
facts of task task-4 = 1 with 0 feedback notice fact(s),
so the second notice was dropped instead of retained for the next turn
```

- 事实级观测：
  - 第二通知交付事实 key `settle-7461736b2d343a313a736574746c65643a30`（解码 `task-4:1:settled:0`），在第一个 follow-up park 期间已提交；
  - 此后 30s 内：模型请求共 7 条，**没有任何请求**携带第二通知材料；
  - 发送侧 3 条 body，全部属于第一任务（accepted A / accepted B / follow A），无第二通知驱动动作；
  - 链上 `task-4` 仅 **1 条**事实（交付事实），**0 条** feedback 通知事实 → 不是“慢”，而是没有保留/待办/后续消费。
- 判定口径：忙时到达的通知必须保留并在后续回合可观测；当前实现以驱动器级单布尔 `firing` 忙时直接返回，未形成可恢复义务。
