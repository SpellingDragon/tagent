## Context

PR36 在 `dfdfa72e` 上已包含常驻消费、跨任务/会话 send、attention 与静止关闭等改动。用户接受破坏性收敛，但不接受以测试绿灯替代架构判断。当前 PR 与 `main` 冲突，且主工作区含有另一现场的未提交修改；本变更只操作 `.quiesce` 工作树。

既有主规格已经覆盖 `consumer-loop-convergence`、`async-task-execution`、`attention-clearance`、`delivery-dispatch-receipts`、`architecture-guardrails`、`production-wiring` 与 `race-gate-coverage`。本轮不得为同一领域事实另造 capability；发现规格冲突时先裁定真实语义，再修改对应既有 requirement。

## Goals / Non-Goals

**Goals:**
- 从公共入口证明不假收束、不丢通知、不双驱动，并保留负向反例。
- 让回执、通知结清、实例身份与关闭各自只有一个权威语义和一个权威状态来源。
- 概念账按新增、删除、改名、权威地位变化分类；删除双轨与修复支架，公共导出面相对基线净减。
- 每批修复经独立新审者复扫，直到关键 frontier 显式为空。

**Non-Goals:**
- 不实现新运行时能力，不重建存储、流式、训练或在线 RL 计划。
- 不保留仅为兼容而存在的双字段、双判据或第二状态机。
- 不通过缩小测试面、放宽门禁、删除症状或修改断言迁就实现。
- 不 commit、不 push、不 merge、不归档；PR 冲突单列，不在本轮隐式 rebase。

## Decisions

### D1 症状与概念双门

运行时门以用户可观察结果为准：公共入口下关闭不得假收束、通知不得丢失、同地址不得双驱动。概念门以事实链、地址、消费循环、任务、通知、审批、回执、关闭为白名单；新名字必须归入其中之一，并证明对应独立领域事实。

候选修法不自动成为验收标准。若当前头已修复某症状，须以基线红或定向变异证明测试能杀死该缺陷；若无法证明，证据等级降为“未证伪”，不得写成“不会再次发生”。

### D2 子域表

| # | 子域 | 既有 spec 能力 | 一句话边界 | 外部依赖 |
|---|---|---|---|---|
| 01 | 消息语义 | `async-task-execution`、`attention-clearance`、`delivery-dispatch-receipts` | 回执、通知结清、委派结果、拒收与待定问题 | 只读取 02 的消费身份，不拥有生命周期 |
| 02 | 实例生命周期 | `consumer-loop-convergence`、`async-task-execution` | 地址唯一性、常驻循环、重入与关闭状态机 | 使用 01 的结清定义，不另建通知账 |
| 03 | 概念/API | `architecture-guardrails`、`fact-vocabulary` | 概念账、导出面、规格冲突与改名识别 | 消费 01/02 的语义裁定，不自行发明语义 |
| 04 | 公共消费者与门禁 | `production-wiring`、`race-gate-coverage` | 正式入口、生产接线、测试证据与 CI 分线 | 对 01—03 只做验证，不替其修产品语义 |

### D3 波次与解锁

- R1：四个只读审者并行，自建公共入口复现并提交 frontier。
- A1：编排者逐条裁定；成立项补成带三锚的孙任务，驳回项附反证，范围外项登记。
- Wn：按孙任务触碰集派发修复；共享文件串行或合单，产品语义与 CI 分线。
- Rn+1：新只读审者复扫修复面和同机制路径；发现新关键问题则回到 A/W。

波次仅为汇报分组。因用户未授权提交，同树依赖解锁表示前一派发单已集成到 `.quiesce` 且复跑通过，不表示已入 main。

### D4 合并与契约规则

实现前冻结任务行的正锚、负锚和消费者锚；执行后不得追认缩水。任何新导出类型、接口、状态名或公共字段必须证明独立领域需求，否则内化或删除。同一机制连续三次修复仍出现新关键缺陷时停线，交用户裁设计。

PR 的 `CONFLICTING` 是独立合并阻断项。不得通过忽略冲突宣称可 merge；是否 rebase/解冲突须用户另行明示。

### D5 三级验收

1. 孙任务：冻结命令原始退出码为 0，测试非空转，负向路径具名且经公共入口。
2. 子域：规格 scenarios 与症状复现逐项映射，生产消费者真实调用，概念账无未裁项。
3. 变更级：双门通过，受影响包竞态与重复回归通过，项目门禁通过，新审者明确“frontier 空”并列出扫描范围。

### D6 概念净减基线

以 `dfdfa72e` 的概念账与导出面为基线，不以更早审查描述代替当前事实。每个修复先列删除项与伴生引用；删除抽象后降为单使用方的伴生结构一并回卷。CI 修复不得新增生产状态、窗口、屏障或公共 API。

### D7 独立放行

审者不得参与同批实现，也不得携带上一轮审者的结论作为扫描清单。每轮只读当前代码与任务验收面；编排者复核证据后才能入账。工作区证据只称“工作区时点”，不冒充提交树或远端 CI 通过。

### D8 方法与测试缝

`grill-with-docs` 按其说明由 `grilling` 与 `domain-modeling` 组合执行；术语裁定同步核对 `docs/GLOSSARY.md`，只有已解决的领域术语才更新词汇表，不把实现机制写进去。修复采用 TDD 垂直切片：先在用户已确认的正式公共入口缝写一个红测试，再写最小实现转绿；重构留在独立审查阶段，不在红绿循环中顺手扩张。

## Risks / Trade-offs

- **[破坏既有调用方]** 删除双轨 API 会扩大编译面 → 先 grep 全部消费者，按语义单元一次性收敛并跑全量构建。
- **[修复引入新补丁]** 局部竞态可能诱惑新增窗口/屏障 → 新结构先过反事实与第二使用方检验，否则回到状态机设计。
- **[基线已变绿]** 最新头可能已修旧症状 → 用基线红或变异杀死证明测试有效，否则只报当前未复现。
- **[门禁时间过长]** 全量与长跑门可能阻塞循环 → 快反馈与长门分开，长门后台运行，但不能省略最终门。
