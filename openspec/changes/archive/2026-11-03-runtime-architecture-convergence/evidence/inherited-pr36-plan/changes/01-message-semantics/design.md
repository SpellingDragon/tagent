## 技术要点

1. 以 `accepted → persisted → transported → consumed → answered/settled` 为观察时间线，逐节点确认实际权威事实；该时间线是审查框架，不预设每个阶段都需要公共状态。
2. 枚举 send、跨任务/会话委派、任务终态通知、审批等待、拒收与重启的公共消费者，核对回执正文是否与被交付内容同源。
3. 对照 `async-task-execution`、`attention-clearance` 与 `delivery-dispatch-receipts`，发现相互矛盾的结清点时提交编排者裁定，不自行选择较易实现的一条。
4. 任何新结构先问“删除后哪条真实业务路径坏”；只服务测试、日志或自身补丁的结构不作为独立概念保留。

## 风险与回退

- 公共 API 改名可能掩盖语义仍重复 → 概念账必须记录行为与消费者差异，而非只比较名称。
- 当前头可能已修旧症状 → 保存当前绿证据，并要求基线红或变异杀死，否则只报未复现。
- R1 不写产品代码；后续修复白名单与三锚在裁定后追加。
