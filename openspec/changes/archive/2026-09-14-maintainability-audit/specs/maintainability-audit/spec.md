## ADDED Requirements

### Requirement: 审计只读性

逐包可维护性审计 SHALL 全程保持只读：审计活动 MUST NOT 修改任何生产代码（*.go 与配置），取证仅限读码、运行既有测试/工具（go vet、go test、-race、-cover）与 git 考古；审计期间发现的可立即修复项 MUST 记录为发现并分流至后续独立变更，而非顺手修改。

#### Scenario: 审计过程中发现可立即修复的缺陷

- **WHEN** 审计者在某包中发现一个可直接修复的缺陷（如缺失的 nil 守卫）
- **THEN** 审计者将其登记为发现（含 file:line 证据、建议立案形态「修复」）并继续审计，且仓库工作区在该变更内不出现任何生产代码改动

### Requirement: 逐包评分卡

审计 SHALL 为每个包产出一张评分卡，覆盖五维：复杂度、耦合与依赖方向、测试覆盖与质量、文档-spec-代码一致性、演进风险；每维 MUST 以 S/A/B/C 定级，且 MUST 附引用具体文件或行为的依据；S 档与 C 档 MUST 各给出至少一个锚点特征以支撑定级可比性。

#### Scenario: 单包评分卡产出

- **WHEN** 审计者完成对某包（如 agent/task）的逐文件审阅
- **THEN** 产出该包评分卡，五维各含定级与依据，且依据中至少引用该包内一个具体符号或文件

#### Scenario: 评分依据不足

- **WHEN** 某维无法给出有依据的定级（如测试覆盖数据缺失）
- **THEN** 该维 MUST 标注「待深钻」而非强行定级，并记入审计开放项

### Requirement: 发现登记纪律

审计的全部发现 SHALL 登记入台账，每条 MUST 含：三级分类之一（🔴 致错/致损、🟠 漂移温床、🟡 卫生债）、file:line 证据、影响路径或反证尝试记录、来源标注（存量 / 本次迭代引入，以 git 考古定性）、建议立案形态（修复 / 重构 / 守护测试 / 文档）；MUST NOT 登记无代码引用的印象式论断。

#### Scenario: 印象式论断被拒绝入账

- **WHEN** 审计者对某处代码产生「这里似乎有并发问题」的怀疑但未做取证
- **THEN** 该条目 MUST 先经取证（race 运行或代码路径推演）取得证据后方可入账；无法取证则记入开放项而非发现

#### Scenario: 发现被反证推翻

- **WHEN** 审计者对某疑似发现复核后确认其非问题
- **THEN** 台账 MUST 保留该反证记录（条目标注「已反证」与理由），而非静默丢弃——与 c5399e2 的 24 疑似逐项定性纪律一致

### Requirement: 汇总台账与改进 backlog

审计 SHALL 产出汇总台账（summary.md）与改进 backlog（backlog.md）：台账 MUST 按严重级排序（🔴 优先）并为每条发现分配稳定编号（F-xx）；backlog MUST 按包归组、引用发现编号、标注建议立案形态与「不修的后果」；二者 MUST 标注审计 base commit。

#### Scenario: 台账排序与编号

- **WHEN** 台账汇总完成
- **THEN** 🔴 级发现列于最前且每条拥有全局唯一 F-xx 编号，backlog 中每条候选均能通过编号回溯到发现详情

#### Scenario: base commit 失效检测

- **WHEN** 审计完成后仓库合入新提交
- **THEN** 读者可通过台账标注的 base commit 判定审计快照时效，且关键发现以符号引用（函数/类型名）辅助定位，行号漂移时仍可按符号复核

### Requirement: 审计方法可复现

审计方法 SHALL 以本 spec 为契约可复现：逐包报告 MUST 记录取证命令（工具、参数、运行范围）使其可重放；五维的定级标准与锚点特征 MUST 在本 spec 内定义完备，使两次独立审计对同一 base 的结论分歧可控。

#### Scenario: 第二次独立复评

- **WHEN** 后续迭代按本 spec 对同一 base commit 复评某包
- **THEN** 复评者能按报告记录的取证命令重放证据，并按同一套定级锚点产出可对比的评分卡；分歧处 MUST 引用锚点特征说明
