# maintainability-audit — 设计

## Context

- 审计对象：main @ `cf006e1`，20 个 Go 包（含根包），约 4.6 万行 Go、87 个主 specs、wiki 十卷、tests/README 真实 LLM 契约矩阵、CI（short + 分子系统 race）；
- 演进背景：六周三轮高强度迭代（D1-D5 平台子系统 → R1-R4 常驻连续性 → build ownership 类型化），dev 单支三天 +7024 行；
- 风险显影：2026-09-13 生产首现 panic（pruneTerminal nil detector，R2 重建与 zombie 对账两个新件相遇）；三份外部评估均点名复杂度反噬；主 specs 曾实证漂移（c5399e2 纠正 24 项疑似、其中 10 项确认非失真——印象式发现的噪声成本已有实测）；
- 既有纪律可复用：openspec 全程留痕、fail-before 回归、fresh-eyes 复审、LEDGER 台账。

## Goals / Non-Goals

**Goals:**

- 逐包逐文件审阅完毕，每包产出一张五维评分卡（复杂度 / 耦合与依赖方向 / 测试覆盖与质量 / 文档-spec-代码一致性 / 演进风险），S/A/B/C 定级且每级附依据；
- 全部发现入台账，🔴/🟠/🟡 三级分类，每条带 file:line 证据与影响路径；
- 汇总为可执行 backlog（每条标注建议立案形态：修复 / 重构 / 守护测试 / 文档），🔴 级标优先窗口；
- 审计方法契约化（spec），后续迭代可按同一方法复评（可重复、可对比）。

**Non-Goals:**

- 不实现任何修复/重构——发现一律分流至后续独立变更；
- 不重写 wiki/README（文档修订属独立变更）；
- 不引入新静态分析依赖（仅用既有工具链：go vet / go test / -race / -cover / grep / git log 考古）;
- 不做性能与安全专项审计（与可维护性交叉处仅记录、不深钻）。

## Decisions

| # | 决策 | 备选 | 理由 |
|---|------|------|------|
| D1 | 五维 S/A/B/C 定级，拒数字分 | 1-10 数字分 | 数字分是伪精度；四档强制定性判断，每档写明锚点特征（如复杂度 S=单文件单一职责且分支可数，C=单文件多职责交织或圈复杂度失控） |
| D2 | 审计单位=包，自叶向根（event → memory 族 → plugin → agent 族 → tool 族 → prompt/evolution/rl → 根包） | 按主题横切（错误处理一致性等） | 用户明示逐包逐文件；主题横切作第二遍交叉补充，横切发现仍记入所属包台账 |
| D3 | 发现证据纪律：file:line 必须 + 反证尝试记录 | 允许印象式条目 | c5399e2 实测 24 疑似中 10 项非失真——印象式噪声成本已付过学费；每条发现须能被第二人按引用复核 |
| D4 | 审计与修复严格分离 | 顺手修复 | 顺手修稀释审计视角、使变更不可回滚、破坏「审计快照」语义；改进动作各自走完整 openspec 流程 |
| D5 | 工具取证为底、人工判读为纲 | 纯工具扫描 | vet/race/cover/grep 考古产出硬数据；命名漂移、契约含混、演进风险只能人工判读 |
| D6 | 每报告标注 base commit + 取证命令可重放 | 无快照标注 | 审完即漂移是必然；绑定 commit 使发现可快速失效检测（file:line 对不上即知已过期） |

## Risks / Trade-offs

- [审计与代码漂移：合入新提交后 file:line 失效] → base commit 标注 + 发现按符号引用（非纯行号）双写，失效可自检；
- [评分主观性引发争议] → 每维在 spec 中定义 S/C 锚点特征；每评分卡必附「依据」列引用具体文件/行为；
- [发现过多致 backlog 失焦] → 台账强制 🔴 优先排序；每条给「不修的后果」一栏，供排序裁决；
- [存量问题与新增问题混淆] → 发现条目强制标注「存量 / 本次迭代引入」（git log 考古定性），存量不追责但入账；
- [审计耗时失控] → 包间相互独立可并行；每包设时间盒（超盒即记录「待深钻」而非强行穷尽）。

## Migration Plan

- 本变更为纯文档产出，无部署/回滚问题；abandon 即丢弃 changes/ 目录即可；
- 后续修复变更引用本审计的发现编号（`audit/summary.md#F-xx`）作为其 Why 的一部分。

## Open Questions

- 「文档-spec-代码一致性」维的事实源：以 openspec/specs 为主，但 12 个 spec 已带状态注记（c5399e2）——一致性判读须同时读注记，注记本身过时也算发现；
- agent 包 3 处存量 race 是否计入：计入，🟠 级、标注「存量」，与 pruneTerminal 修复中已顺手消除的 1 处区分；
- 逐包报告粒度：20 包中 tool/govx、tool/memoryx 等小包（<500 行）是否合并简报——按「文件数 ≤3 且行数 ≤500 可两包合一简报」执行，评分卡仍逐包独立。
