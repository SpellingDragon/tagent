## Context

tagent 是基于 trpc-agent-go v1.7.0 的 Agent 框架，核心架构围绕"事件驱动 + 内存中心 + 视图转换"三大原则设计。项目经过 Phase 1-7 多轮迭代，部分机制在迭代中被移除或重构。当前代码库包含 53 个 Go 源文件，分布在 agent、memory、plugin、event、tool、prompt 六个包中。

审查需要对照设计目标检查实现一致性，但不应预设具体发现——审查的目的是独立、客观地识别偏移，而非验证已知问题。

## Goals / Non-Goals

**Goals:**
- 定义可执行的审查方法论，使审查者能够系统性地覆盖全部代码
- 建立 6 项设计目标 × 3 项横向维度 × 1 项端到端追踪维度的审查矩阵，确保无盲区
- 产出结构化的审查报告，按严重级别分类，可直接驱动后续修复变更

**Non-Goals:**
- 不在审查前预设具体问题或发现
- 不直接修复代码
- 不评价新功能设计或未实现部分的架构合理性
- 不做性能基准测试或负载测试

## Decisions

### D1：逐模块审查 + 横向维度交叉验证 + 端到端数据链追踪

**选择**：采用"逐模块纵深审查 + 横向维度交叉验证 + 端到端数据链追踪"三阶段方法。

**理由**：逐模块审查确保每个文件的代码都被阅读和理解；横向维度交叉验证确保跨模块的系统性问题（如并发安全、接口契约一致性）不被遗漏；端到端数据链追踪确保从生产入口到最终执行点的每条配置链、生命周期链、数据传递链、状态回收链都完整无断点。三阶段方法比两阶段方法覆盖更完整，能发现"实现存在但未接线"、"字段定义但未使用"、"组件创建但未启动"等跨模块断链问题。

**流程**：
1. **阶段一（逐模块）**：按组合根 → agent → memory → plugin → event → tool → prompt 的依赖顺序，逐文件阅读代码，对照 6 项设计目标记录发现
2. **阶段二（横向）**：以 3 项横向维度（并发安全、代码一致性、接口契约）为线索，跨模块交叉验证，识别系统性问题
3. **阶段三（端到端数据链）**：从生产入口（tagent.go resolveMemoryStore / builtin.go 工厂）出发，对每条数据链进行端到端追踪：
   - **配置链**：YAML 配置 → config.go 解析 → 工厂函数 → 子组件构造 → 实际执行点，验证每个配置项到达最终执行点
   - **生命周期链**：生产入口 → 组件构造（NewXXX）→ 后台启动（Start）→ 停止（Stop），验证每个有 Start() 的组件在生产代码中被创建和启动
   - **数据传递链**：函数参数定义 → 逐级传递 → 最终使用点，验证不存在"接收了参数但从未使用"的断链
   - **状态回收链**：资源创建 → 状态检测 → 回收/清理，验证回收机制在生产代码中被启动且有效执行

### D2：严重级别定义

**选择**：采用 4 级严重级别分类。

**理由**：明确的严重级别使审查报告可直接驱动修复优先级排序。

| 级别 | 定义 | 示例特征 |
|------|------|----------|
| P0 | 功能性退化——设计目标的核心承诺未兑现 | 数据通道断裂、关键功能无效、后台组件未在生产代码中创建/启动 |
| P1 | 安全隐患——可能导致 panic、数据竞争或状态错乱 | 并发竞态、资源泄漏、跨路径权限不对称 |
| P2 | 代码质量——不影响正确性但增加维护风险 | 过时注释、死代码、stub 未接入 |
| P3 | 文档过时——文档与实现不一致 | wiki 描述已废弃机制 |

### D3：审查报告格式

**选择**：审查报告按"设计目标维度 + 横向维度 + 端到端数据链维度"组织，每项发现包含：模块/文件、代码位置、问题描述、严重级别、根因分析、修复建议。

**理由**：按设计目标维度组织使报告与审核标准一一对应，便于验证审查完整性。端到端数据链维度作为独立章节，专门记录跨模块断链发现。修复建议为后续修复变更提供输入但不强制约束。

### D4：审查者独立性

**选择**：proposal 不预设具体问题，审查者仅依据审核标准和代码本身进行判断。

**理由**：预设具体问题会导致"确认偏误"——审查者只验证已知问题而忽略未知问题。中立的审核标准使审查者能够独立发现已知和未知的偏移。

## Risks / Trade-offs

- **[审查覆盖盲区]** → 逐模块审查可能遗漏跨模块交互问题。缓解：阶段二横向维度交叉验证 + 阶段三端到端数据链追踪专门覆盖跨模块交互和接线完整性。

- **[审核标准主观性]** → 6 项设计目标的解释可能因审查者而异。缓解：每项标准在 specs 中定义可测试的检查项，减少主观判断空间。

- **[审查报告过长]** → 53 个文件的逐代码审查可能产出冗长报告。缓解：按严重级别聚焦，P3 级发现（文档过时）可合并为列表项。

- **[数据链追踪遗漏]** → 阶段三端到端数据链追踪可能遗漏未知的链路类型。缓解：以"配置链、生命周期链、数据传递链、状态回收链"四类为基线，审查过程中如发现新链路类型则追加追踪。
