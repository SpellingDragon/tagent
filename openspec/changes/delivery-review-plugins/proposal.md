# 发送插件 × 审核插件：投递与审批解耦

## 症状（验收矩阵第一行，用户原话直译）

1. **"发送响应消息对于 agent 来说是工具吗？为什么总会有 send ok？是 agent 主动选择向自己的 output 管线 send 消息吗？很奇怪。"**
   → 直译测试 G-A：entry 请求的工具面**没有 send**；模型说话只经回合正文，正文经自动投递到达用户（恰一条，无回执可复述）。
2. **"发送和审核应当通过不同插件分开，审核插件负责统一做需要审核的语义映射。"**
   → 直译测试 G-B：对外投递在**发送插件**出口处经**审核插件**裁决——配置 hold 规则时投递挂起（用户零消息）、批准后**恰一条**补投、拒绝后零投递且有审计；审核裁决的输入是投递语义（内容 + 血统 + 目标），不依赖 send 工具存在。
3. 前置症状（回归）：审批 hold 不因 send 移除而失去对象；收尾轮治理不依赖 send。

## Why

send 作为模型工具是"说话通道"与"审批对象"的耦合点：模型对自己输出管线发消息（回执复述、内部记账外泄、一次请求 7 条消息——真机实证），而审批（governance 插件，已按 tool name/args/trigger_source 统一映射）唯一能拦的发送对象就是 send 工具。移除 send 必须同时给审批找到新的投递语义挂点，否则审批对发送的裁决随工具一起消失（3 个既有产品语义测试红）。

## What Changes

- **发送插件**：宿主投递的唯一出口（`deliverFresh` 与未来跨代理发送共用）；投递前把投递语义交审核插件裁决。
- **审核插件扩展第四类语义**：投递（Delivery）——输入内容、血统、目标；裁决三态沿用 allow/record/hold；**hold 是等待**（批准后补投，拒绝则丢弃并留审计）。
- **entry 不再授权 send**：模型无"对自己输出管线说话"的通道；send 仅作为跨代理通信工具保留（当前无消费者，代码保留不装配）。
- **测试迁移**：审批 hold / 收尾轮治理场景的对象从"send 调用"迁移到"投递语义"；新增症状 G-A / G-B 两个直译测试。
- **不做的**：不默认拦截投递（审核默认 allow，hold 需配置规则显式触发——行为面变化最小）；不改 governance 的三态与四级风险定义。

## Capabilities

### New Capabilities

- `delivery-plugin`：投递唯一出口及"投递前审核"衔接；hold 挂起/批准补投/拒绝丢弃三态。

### Modified Capabilities

- `governance`（审核插件）：语义映射增加投递类（内容/血统/目标）；三态与风险级不变。
- `quiet-receipts`（间接）：entry 工具面收缩后 send 回执不再是"对用户说话的常用路径"，`ok` 语义限于跨代理 send。

## Impact

- 代码：`host.go`（deliverFresh 前置裁决 + hold 挂起/补投）、`api/plugin/governance.go`（投递语义）、`examples/wechat-bot/tagent.yaml`（entry 去 send）、smoke 台架（send 脚本路径迁移）。
- 合同：主规格循环边界加"投递前审核"场景；v1/v2 合同的审批场景迁移。
- 用户裁定：发送与审核分离为两个插件；审核统一做语义映射；hold=批准后补投（governance 既有"hold is a wait"契约）。

## 必答一问

"本案完成后，'模型对自己输出管线 send 消息'还会发生吗？"——不会：entry 无 send 工具，说话唯一路径是回合正文 → 发送插件 → 投递（可被审核 hold）。证据=G-A/G-B 红转绿 + 回滚即红。
