处置概念依据
对外收拢为一个名字blob + ref → 「原文仓」两个部件一个职责：字节仓（CAS 去重）+ 账目（scope 授权/租约/血缘）。使用者永远只见「原文仓」；blob/ref 是它的内部件名。
席位 + 消费回执 + settle attempt → 「通知消费账」三个记录同管一件事：一条通知被谁认领、是否已消费、尝试到哪。合并讲述，不合并实现。
降为实现细节分片 / snapshot.json / kvBatch物理布局（性能设施），不进概念面——只在讲「为什么快」时出现。
真复杂度，不能减链不可变 × 原文可过期必须两层：链永在（回放）与原文按策略过期（retention）是两条正交生命周期，塞一层则两者其一不成立。
ref 的 scope 隔离多会话真需求：越权读作不存在、零泄漏——删掉则跨会话原文互窥。
先登记 owed、后消费回执跨批无事务下的崩溃不漏送；删掉则发送途中崩溃=永久丢结果。
relations.journal 因果日志「谁消费了谁」的独立可重放面；塞进事实链则因果与正文耦合，重放装不上轻链。
一句话总纲
链管身份与因果（轻、恒重放）· 原文仓管字节（重、按需取、可过期）· 账本管责任（受理/消费/交付）· 其余一切现算。
