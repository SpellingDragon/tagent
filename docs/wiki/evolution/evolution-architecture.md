# 自我改进（evolution）架构与契约

`evolution` 包实现"agent 改自己的提示词/技能/脚本"这条通道：改动**默认即生效**，包只负责**留痕、评估与可安全回滚**。本文是该通道所有跨模块约定的权威描述。

## 一、四条设计前提

| 前提 | 含义 | 违反后果 |
|---|---|---|
| 文件即真源 | 改文件立刻生效，登记不是生效的前提 | 把登记做成生效前提，会让 agent 在未登记时静默不生效 |
| 复用 git | 版本、留痕、回滚全部用 git 原语，**零自建版本库** | 自建台账必然与 git 分叉 |
| 建议式而非动手 | 评估出劣化只**产出建议**（写 evaluation 事件、进反思 digest），框架不自动回滚 | 自动回滚会在证据不足时错杀低风险改动 |
| 分层红线 | `evolution` **不 import** `governance`，治理类事件直写存储（与 `DiffLaneRouter` 同一取向） | 反向依赖会让评估器无法独立测试与复用 |

<a id="refine"></a>

## 二、`refine` 工具的三个操作

- `register`：产物落盘后登记留痕（`paths` ＋ `note`，note 要求写"痛点 → 产物 → 预期收益"）→ 生成改进 commit → 写 improvement 事件 → **开评估窗口**。未登记的改进既无评估保护也无法安全回滚。
- `status`：改进台账 ＋ 各窗口评估结论 ＋ 未登记产物提醒。
- `rollback`：安全回滚指定改进 commit（可前缀）。**回滚是终态**：不写事件、不再开窗口（信任执行者）。

曾经存在的 `diff` 操作已删除——`exec git diff` 可达，不需要再造一层。

`nothing-to-commit` **不是错误**：以正常 result 消息渗透给调用方。同理，revert 冲突也不打断回合，而是把 git 输出与处置指引（`--abort` 放弃 / 解决后 `--continue`）作为结果返回。

工具只注册给主 agent（entry only），装配顺序上**先于治理包裹**追加，使自我改进调用本身也受治理约束。

<a id="git-safety"></a>
## 三、git 原语层的四条安全约束

1. **改进标记行首锚定**：改进 commit 的 message 以 `[self-improve]` 行首起。生成、过滤、回滚校验三处共享同一常量。行首锚定天然排除 revert 产生的 `Revert "[self-improve] …"`——否则回滚记录会被当成新的改进再次评估。
2. **`--grep` 必须正则转义**：`[self-improve]` 的方括号不转义会被当作字符类，任何以 `i` 开头的 subject 都会误命中。
3. **只 add/commit 显式 pathspec，且 commit 用 `--only`**：裸 `git commit` 会提交**整个 index**，从而卷入用户手工暂存的内容或上次失败遗留的暂存文件——回滚时会连带回滚用户的工作。绝不用 `-A`。
4. **每次调用局部注入 git 身份**（`-c user.email/user.name`）：裸环境（CI、容器）没有全局 git config，否则 commit 直接失败。不依赖用户全局配置同样让生产受益。

### 受控路径匹配

`path.Match` 不支持 `**`，因此按 `/` 分段递归匹配：`**` 吃任意多段（含零段），普通段仍是单段通配语义（段内不得含 `/`）。待校验路径先做**三态归一**（绝对路径 / 相对运行目录 / 相对 workspace 一律折成"相对运行目录的 clean 路径"），否则同一文件会因书写形式不同而绕过或误拦受控清单。

回滚前的标记校验是**保护用户提交不被误 revert** 的闸；非 git 工作区下启动自检只告警不阻断（改文件仍生效，只是没有留痕与评估保护）——闸不是墙。

<a id="evidence-window"></a>
## 四、评估窗口：窗口起点必须锚在激活时刻

快道是"先生效、后验评估、劣化即建议回滚"，因此需要 canary 期间的**表现证据**。

### 窗口起点

证据窗口以 bundle（或改进 sha）的**激活时刻**为起点，而不是固定回看窗。原因：当 canary 保持期为 0（激活即评估）时，固定回看窗里全是**旧 bundle 的数据**，对新 bundle 毫无判别力，"劣化即回滚"形同虚设。激活时刻若早于回看窗，则用 `now - window` 兜底，避免窗口无界扩大。

窗口时刻表是**内存态、不持久化**：重启后激活记录清零，对重启前激活的 bundle 回退固定回看窗。这是**有意的可接受降级**（重启后 canary 通常已结算，评估主要针对重启后新激活者），而非静默缺陷；持久化时刻表为后续增强。

### 事件读取必须"服务端时间过滤 ＋ 倒序"

常驻 agent 的分区事件量远大于查询上限。若用**升序**取前 N 条，拿到的永远是最旧的 N 条，全部早于窗口起点而被客户端滤净 ⇒ `TurnCount = 0` ⇒ **后验评估永久静默失效**（看起来"健康"，其实什么都没看）。因此必须：服务端按 `StartTime` 过滤 ＋ `timestamp_desc` 排序；截断时牺牲最旧、保住观察窗。客户端的时间判断保留为兜底。同一条理由适用于"找最新改进"与"拉全部评估结论"两处查询——升序会取到最旧的改进。

### 归属与计数口径

- **带章事件按 `bundle_id` 精确 join**：事件归属它真实的 bundle，其他 bundle 的事件不计入本窗口证据。无章事件（历史时期或未启用自进化时产生）回退到时间窗归属。
- **`TurnCount` 只数真实 turn 边界**（用户输入型事件），不再计全部事件数。旧口径把事件总数当分母，会稀释拒绝率/负反馈率，使判据**结构上不可达**。
- 反馈判定优先读元数据里的冗余 verdict（写入时冗余，不依赖内容序列化格式）；对内容做子串匹配只是修复前落库的旧事件的后备路径。
- 治理 subtype 的字面量必须引用 `event` 包的权威常量。此前复制 `"denial"`/`"approval"` 字面量存在**静默漂移**风险：常量一改，`DenialCount` 归零、指标闸永不 breach、确定性回滚防线整条失效。

## 五、双回滚触发（互补，不是二选一）

| 触发 | 特性 | 抓什么 |
|---|---|---|
| `MetricGuardrail` | 确定性阈值，快、廉价，**先于** LLM 判定 | 明确违约（拒绝率/操作率/负反馈率超阈） |
| `LLMJudgeEvaluator` | 慢、质性 | 阈值未覆盖的整体劣化 |

### 指标闸

默认阈值：治理拒绝率 0.3、critical 操作率 0.2、负反馈率 0.3、最小样本 5。**样本不足或证据收集失败一律不判劣化**（保守，防抖动错杀）。

负反馈率阈值支持**显式禁用**：配成负值即跳过该判据。此前"禁用"依赖填一个 `>1` 的不可达值，语义隐晦且容易被当成配置错误。

默认阈值与 `judge_timeout_seconds` 都遵循**零值不等于关闭**：留空或填 0 一律落到上面这组内部默认，只有显式给出值才覆盖；要停用某一项判据，必须用该项规定的显式禁用形态（如负反馈率阈值配成负值），不能靠填 0 表达「不要这项」。装配侧因此把配置值原样交下去，由被装配方解释零值。

### LLM 评审的保守原则

**只有模型明确判出劣化（score 低于阈值）才触发回滚建议**；以下情形一律保守通过：judge 未配置、证据收集失败、样本不足、模型调用失败、响应解析失败。评审器内部消化模型错误，绝不向发布管理器抛错——否则 judge 暂时不可用就会回滚掉已激活的低风险变更（确定性防线仍由指标闸承担）。

解析侧有两条必须记住的细节：

1. `score` 用**指针**接收以区分"字段缺失"。合法 JSON 但缺 `score`（或大小写不符、显式 null）时，零值 `0` 会被当成"严重劣化"而触发回滚——这直接违背保守原则。缺失即保守通过。
2. 响应可能是 markdown fence 包裹或带前后缀文字，需先提取首个 `{ … }`；score 越界夹到 `[0,1]`；模型没给理由时补占位文本。

<a id="verdict-states"></a>
## 六、评估结论四态与建议事件

结论只有四态：`healthy` / `degraded` / `insufficient` / `pending`。**样本不足或评估失败不得冒充 healthy**——必须写 `insufficient` 并附原因。治理开关未启用时，拒绝率与 critical 判据在结构上不可用，结论理由里必须显式声明"信号不可用"，不能让零计数看起来像健康证据。

劣化时写出的建议包含可执行的下一步（`refine rollback <sha>`，并提示可先 `git diff` 复核），随反思 digest 渗透给主 agent。

## 七、版本章缓存

盖章用的"最新改进 sha"是**性能层缓存**，真源始终是 improvement 事件本身：首次读取时做一次惰性恢复（按上述倒序查询最新一条 register），之后由登记路径更新。缓存丢失只会退化为一次重查，不会丢事实。

<a id="test-facts"></a>
## 九、测试接线时必须钉住的三条事实

这三条各自都造成过一次"测试绿而语义没被验证"，写测试时必须照做：

1. **种进存储的事件必须用真实 Snowflake key**。读回时分区是从 key 自身推导的（`PartitionIDFromEventKey`），随手写的裸整数 key 会让批量读回**静默丢事件**——测试看起来过了断言，实际什么都没读到。
2. **`git status --porcelain` 对未跟踪内容取目录级展示**（列 `workspace/` 而非 `workspace/x.txt`）。判断"无关改动没被卷进改进 commit"时，断言要按目录前缀写，否则会在正确的实现上误报失败。
3. **`encoding/json` 的字段匹配默认大小写不敏感**：`{"Score":0.9}` 会命中 `json:"score"` 并按正常值解析，**不算字段缺失**、不触发保守分支。"缺失即保守"的回归只覆盖真正缺失与显式 `null` 两种形态。

另外，评估结论的两条 fail-closed 不变量是发布环依赖的，必须作为成对断言存在（含一个反向对照，证明"信号不可用"的注解确实来自开关而非常量字符串）：

- 评估器/证据不可用 ⇒ 结论必须是显式的 `insufficient`，绝不静默记成 `healthy`；
- 治理信号关闭 ⇒ 即便结论是 `healthy`，理由里也必须带上"信号不可用"的注解，不能让读者以为拒绝率与 critical 已被查看过。

## 八、评估定时与生命周期

一次登记对应**一次性窗口快照**：延迟到期评估一次，不轮询。停止信号可**抢占**等待（不必等满延迟），被抢占时评估不发生、窗口无结论，如实降级而不伪造。登记与停止的并发通过互斥串行化，避免等待组的 Add/Wait 误用。
