# 治理：分级处置、批准通道与预算账本

本页承载 `agent/governance` 的判据。它的定位是**在工具执行前做分级裁决**，并且把"被拒绝"当作可核查的资产保留下来，而不是一个错误返回值。

<a id="enforcement-modes"></a>
## 一、两种执行档：是否真的拒绝，只由这一档决定

| 档 | 行为 |
|---|---|
| `warn`（缺省） | 违规被记账并暴露，但**不阻断**执行 |
| `strict` | 违规判为**拒绝** |

门未启用时一律放行；门本体为 `nil` 时访问器返回 `nil`/零值配置（即未启用）而不是 panic——治理是可选层，不能因为没接线就把主链路打死。

<a id="disposition-and-risk"></a>
## 二、风险分级与三种处置

风险从低到高分四档，**最高档恒走异步批准**，不因放行策略跳过。裁决产出处置三选一：

| 处置 | 后果 |
|---|---|
| `allow` | 放行内层工具，无额外留痕要求 |
| `record` | 放行，但要求把这次执行记入审计账本 |
| `hold` | **拦下**：交给批准流程，内层工具不执行；获批后才委托内层 |

`hold` 与"直接拒绝"走同一条外显路径（都不执行内层），区别在于前者可以被批准后续上。分级输入是纯数据（工具名、参数 JSON、触发源），规则本身是数据驱动的纯函数匹配。

<a id="approval-channel"></a>
## 三、批准通道：外部裁决，一请求一文件

批准状态四态各有明确含义：`pending`（等待裁决，此时被治理的操作不执行）、`approved`、`denied`、`expired`（**超期未裁决按未获批准处理，不得事后凭旧请求继续执行**）。

通道侧的三条约束：通道故障**不阻塞**主链路（拿不到裁决就维持等待，而不是当作放行或当作崩溃）；重扫按节流窗口进行，窗口到期后恢复；过期文件被清理。请求文件可被外部审批者读写，因此"运行时可见的重扫"是必需的——外部刚写下的裁决必须能在下一次扫描中被看到。

<a id="budget-epoch"></a>
## 四、预算与 epoch

预算管理器有"限额与耗尽"两种可判定状态。预算快照**携带 epoch 一起持久化**；读回时若快照缺失、解析失败或其中 epoch 为 0，就**不覆盖**当前 epoch。若反过来让缺失值把 epoch 归零，累计消耗会被误当成"新开始"，预算门形同虚设。

<a id="denial-ledger"></a>
## 五、拒绝账本：拒绝是一等资产

一次拒绝要同时留下两样东西：账本记录，以及一条治理事件（供宿主与观测面看到）。账本对存储采用**迟绑定**且 **nil 安全**：没有存储时不 panic，也不静默丢掉记录的意义——模型需要据此自纠，而不是拿到一个 panic 或空返回值。

<a id="goal-registry"></a>
## 六、目标登记：从事件重放，四态可判定

目标状态四态：`active`（在途，占用治理预算并参与门禁判定）、`achieved`（达成，不计入在途）、`abandoned`（主动放弃）、`expired`（超期未达成；与放弃区分，用于统计与预算归因）。登记表可从事件重放重建，并发访问安全；无存储时退化为内存态而不是失败。

## 已知缺口与演进方向

- `warn` 是缺省档，意味着"接了治理但没配 strict"的系统实际不阻断任何事——这一事实目前只能从配置读出来，没有运行时可见信号；
- 批准通道依赖文件轮询，缺一个把"谁批的、依据什么"结构化下来的字段；
- 预算 epoch 的语义只由测试钉住，缺一次跨重启的实测报告。
