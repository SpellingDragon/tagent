# tmux 会话的存活判定与状态通知

本页承载"什么时候算完成、什么时候算活着、什么时候才该通知模型"的判据。**这些判据的失效表现都不是报错，而是误杀健康任务或重复投递通知**。

<a id="quiet-vs-dead"></a>
## 一、静默不等于假死

| 情形 | 判定 | 为什么 |
|---|---|---|
| 输出长时间无变化，但**进程存活**且**未显式声明静默超时** | 记一条日志后判 `Stable`，**不击杀会话** | 静默是长任务常态（编译/训练/下载/长 sleep）；"静默→心跳→杀"会误杀健康任务 |
| 输出无变化、进程存活、**且**该会话显式声明了静默超时阈值 | 才进入假死判定 | 阈值是 **opt-in**：只有显式声明才把"静默"当信号 |
| 无显式阈值时 | 阈值一律回落到配置默认值 | `0/省略` 表示"未声明"，不表示"立即判死" |

同类校验：**`quiet_timeout` 不得低于稳定窗**（非 TUI 60s、TUI 90s；更小值在 `Call` 校验阶段直接拒绝）、**TTL 不得为负**（`0` 是"用配置默认"，系统里不存在"无限"）、**`mode` 与 `is_tui` 互斥**。

<a id="liveness-first"></a>
## 二、判活先看进程，绝不向会话注入按键

判活**优先查进程存活**（pane 退出状态），而不是注入一次心跳回显：向正在编译的进程的标准输入里塞 `echo` 会**污染它的输入流**。心跳只在"必须区分假活"时使用，其结果只把会话标成"假活"，不直接标完成。

<a id="notify-gates"></a>
## 三、状态跃迁通知的三个门（AND）

1. 注册了回调（全局或该会话专属）；
2. **新旧状态都"有意义"**——假死/假活这类判定中间态不作为跃迁的两端；
3. 新状态与**上一次已通知的状态**不同（按"上次已通知"比较，不是"上次检测到的状态"——否则一次未被通知的抖动会让后续真实跃迁被吞掉）。

会话被移除时必须同时清掉专属回调与"上次已通知"记录，否则同名新会话会继承旧的去重基线。

<a id="fake-alive-restart"></a>
## 四、假活的重启保持同一身份

以**原会话 ID** 重启：成功则重置稳定度元数据，下一轮自然从"假活"回到"运行中"；失败则**不改动状态**，交给下一轮重评。用新 ID 重开会话会让所有按 ID 等待结果的消费者拿不到回执。

<a id="truthful-tail"></a>
## 五、交付给消费者的必须是真实尾帧

保留**最后一次运行中轮询捕获的输出**作为终态输出，不用中途的部分捕获覆盖它——消费者要按尾部断言（例如结束标记）。由 `list-sessions` 确定性判死之后，不再被 `display-message` 的错误输出误导成"还活着"。

<a id="hit-counting"></a>
## 六、命中计数只增不减

"完成标记命中数"按**累计增量**记账：本轮命中数少于上次记录时（pane 滚动或截断导致可见行变少），增量按 `0` 处理而**不是**回退计数——宁可少报一次，也不因输出窗口滑动而伪报命中。增量为 0 时不产生任何通知。

<a id="named-session-singleton"></a>
## 七、命名会话不得被静默双开

同名会话已存在时**直接报错**，要求调用方先停止它或走恢复路径，而不是再起一个：两个开发服务器抢同一端口是典型故障，静默双开会让第二个进程以"看起来成功"的方式启动。

<a id="restart-takeover"></a>
## 八、重启后的接管与流式日志

重挂是 best-effort：meta 文件读不到就跳过该会话，会话在 tmux 里**看起来仍然存活**却不再被监视。因此这份落盘目录是跨进程共享可写状态——测试必须走私有目录（`WithResidentMetaDir(t.TempDir())` 或 `residentMetaDirOverride`），既不得读写进程默认目录，更不得 `RemoveAll` 它：一次整目录清扫足以让另一进程正在进行的换代重挂静默失去会话，症状是"任务永远停在 suspect、等待预算耗尽"而非报错。该不变量由 `TestResidentMetaDirHygiene` 静态守住。

- 只接管**命名前缀**且元数据模式为常驻/交互的会话；元数据损坏 ⇒ 记警告并跳过（**不因个别坏文件中断整轮恢复**）。
- 已跟踪的会话**不再重复接管，但仍刷新新鲜锚点**：多实例共享同一批会话时，锚点不刷新会让别的实例持有的会话被本侧清扫误杀。
- 接管完成后立即清扫"未被任何实例接管且已过 TTL"的会话。
- 一处归属只有一条清理路径：判定结束时由同一个取消回调依次做"杀会话 → 从监控移除 → 删除常驻元数据"，不留半清理状态。

<a id="pipe-log"></a>
## 九、流式记录：从建会话那一刻起完整，结束后归档而非删除

建会话时先把管道文件**清空创建**，再挂 `pipe-pane -o`——合起来保证"从启动起的完整输出"落在同一个文件里，不漏最早几行，也不混入上一会话残留。会话被杀时管道文件**改名归档**而不是删除（只有归档失败才回退删除并记警告）：面板输出会被滚动截断，它是"这个会话到底做了什么"的**唯一完整记录**。`pipe-pane` 运行在 tmux 服务端内，重启期间仍在追加，因此新检测器读同一路径、从偏移 0 起即可。

<a id="error-visibility"></a>
<a id="failure-polarity"></a>
## 十、错误的可见性：框架级异常必须落日志，配额与竞态要给出可行动的提示

| 情形 | 行为 | 为什么 |
|---|---|---|
| 建会话失败 | 错误串里**并上 tmux 的 stderr 原文** | 只报"exit status 1"会让真实原因（权限、server 崩溃、参数非法）永远看不见 |
| 会话已建起来、但其后的设置项失败 | 记警告，**不**判创建失败 | 会话可用；误报会让调用方重复发起并撞上"同名已存在"守卫 |
| tmux 层异常（框架/环境级） | 先落 error 日志再返回错误 | 模型侧只会看到一次工具失败；没有日志就无从判断是环境还是命令问题 |
| 常驻会话配额已满 | 明确报错并提示先停掉某个现有常驻会话 | 拒绝要**可行动**，否则模型只会重试同一动作 |

<a id="known-gaps"></a>
## 已知缺口与演进方向

- 假活重启依赖被重启进程本身可重入；对不幂等的命令，目前只能等其滑向假死，没有补偿路径。
- 稳定度阈值与静默阈值目前按会话类型分档取值，缺一次实测标定。
