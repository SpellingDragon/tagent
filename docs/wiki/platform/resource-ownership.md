# 运行时资源所有权（共享后端的租约、代际与封路）

<a id="overview"></a>
## 一、机制定位

`RuntimeResources` 是持久后端的**唯一属主登记处**：一条登记对应一个 `(kind, canonical path)` 键，每个消费者从中取一份**租约**，后端只由登记处开一次、也只由登记处关一次。子 agent、验证壳与执行代都是**借用者**，MUST NOT 关闭不属于自己的那份资源。

- 键的 canonical 化：既存路径解符号链接；路径尚未存在时回落到 `Abs`+`Clean`，并把**最近的既存父目录**解链接——同一物理目录的不同写法必须落进同一条登记。
- 空路径（每实例独占的隔离 store）**旁路整个登记处**：每个构造各自拥有、各自关闭。
- 目录写权由 `<path>/.tagent-writer.lock` 上的进程间 flock 保证，且**在打开后端之前取得**：后端一被打开就带着可写的后台生产者，先取锁才不给跨进程第二写者留窗口。

<a id="last-lease-close"></a>
## 二、末租约才关闭，关闭之后是真重开

每一次释放只减一份计数；计数仍大于零时后端**保持打开**，幸存借用者照常读写、后台生产者照常运行。最后一个租约释放才关闭后端、交还目录写权并移除登记，因此下一次构造拿到的是**真正重开的实例**（读得到上一代持久化的数据、带全新的后台生命周期），而不是一个已关的死对象。

关闭与后端 I/O 都不持全局登记锁：登记簿的记账在短临界区内完成，可能很慢的最终关闭在其外进行——别的目录的构造不会排在这场 flush 后面。

<a id="fingerprint-conflict"></a>
## 三、不兼容配置必须拒绝，零行为差异轴不得制造假冲突

同一路径已开着时，请求侧的配置指纹与登记侧不一致就**显式拒绝**：既不创建第二写者，也不静默沿用先到的配置。竞争情形同样收敛——两个构造同时开同一路径时，登记锁内复检，输家**丢弃自己刚建的那份**并改共享赢家已发布的实例。丢弃也是一次拆除：**未确认丢弃已停就绝不交还自己那份写锁**（该分支在现行 per-key 串行化下不可达，保留为防御腿，见末节）。

指纹只收**影响行为的轴**：类型、路径、生命周期、引擎、rustviking 可执行文件。两值行为恒同的轴**MUST NOT 进指纹**——否则两份行为完全一致的配置会被判成假冲突；判别面是同指纹下两个句柄共享同一活实例（互见写入、不重建）。

<a id="release-generation"></a>
## 四、释放幂等，且陈旧释放改不动新代

每个租约的释放闭包**至多生效一次**，后续调用返回首次的结果——第二次 `Close` 之类的重复释放不可能把别人的计数多减一份。释放还带**代际身份**：只有当代登记仍在且代号为该租约所持有的那一代才生效；同一路径已经被新一代接手时，旧一代留下的释放闭包**什么也不改**。

<a id="per-key-coordination"></a>
## 五、同路径的开与关共用一把 per-key 互斥

同一路径的"开"与"最后一次释放"排在**同一把 per-key 互斥锁**上：同路径重开必须**等上一代关完**再开，而不是看到"登记已没了、写锁还在"就误报锁被占用；无关路径各有各的互斥锁，绝不被别人家的慢 flush 挡住。并发同路径的获取由此串行化，全部持有者得到**同一个实例**。

取锁顺序恒为 **per-key 互斥 → 登记簿锁**，且登记簿锁从不跨过后端 I/O；反过来取就会与上述串行化互锁成死锁。封路条目的重登记也走同一把 per-key 互斥，所以"摘除旧条目"与"放回封路条目"之间不可能有新一代发布进去。

<a id="single-writer"></a>
## 六、目录级单 writer

一个物理目录同时只允许一个写者：第二个持有者（另一个进程，或同进程另一个打开的文件描述）非阻塞抢锁必须失败并具名报"被占用"。释放后可重新取得；**进程崩溃由 OS 自动释放 flock**，不存在遗留标记把目录永久锁死。

边界：flock 只在**本地卷**上是这个契约，NFS 上它是建议性的。

<a id="close-order"></a>
## 七、关闭次序与错误必须上达调用方

最终释放按依赖序拆除：**先停遗忘生产者**（压缩器与生命周期扫描会在清扫时回调引擎的向量移除器），**再停并等待引擎工作协程**（其排空仍写活着的 KV），**最后 flush 并关闭后端**。

关闭错误 MUST NOT 被吞成"安全关闭"：它必须回到释放的调用方，并且重复释放也拿得到同一份错误。后端 flush 失败照样交还写权（引擎已确认停止，重开是安全的），只是错误如实返回——不得谎报持久化成功。

<a id="poisoned-seal"></a>
## 八、无法确认停止＝该路径封到进程重启

引擎停止**无法确认**时，绝不把路径交给新一代：登记处保留一个**显式的 poisoned 条目**——强引用着原来的 store、engine、锁文件与失败原因——后续同路径获取一律明确失败并带上那条记录的原因。锁的保有**从不依赖"GC 恰好没回收一个不可达 fd"**；主动 GC 也削弱不了封路。

封路的优先级高于冲突记账：同一路径即使换了另一份指纹，报的仍是"被封住"而不是"冲突"。无关路径不受影响。

**该状态没有解封出口**：确认停止之后也不会自动解封，恢复方式是**重启进程**。这是刻意的 per-path fail-closed——宁可拒绝整条路径，也不可能与一个可能还活着的生产者并写同一目录。**引擎侧**的两条触发腿在现行引擎里都是真实的（索引排空超时、待刷向量超时），不是未来才可能出现的形状；它们汇入下面登记处侧的形态①。

同一纪律覆盖构建侧：构建失败而**回收无法确认**时，写权继续保持、路径同样被封；回收确认成功才交还写权，让下一次获取能干净重试。

**登记处层面的四种触发形态**（都不依赖"运气好没出事"）：① 最终释放无法确认引擎工作协程已停；② 已确认停止、但**写锁的释放**无法确认；③ 构建失败且**部分建成资源的回收**无法确认；④ 构建失败后**写锁释放**也无法确认。四种都把失败原因记进条目（①若连错误都没有则补一条"引擎工作协程停止未确认"，不留空白）。

形态②与③④ 的条目形态不同：释放侧封路时条目仍强引用 store/engine/锁文件；**构建侧封路时资源根本没建成，条目只带锁文件与失败原因**（不带 store/engine）——被封的永远是"这条路径的写权"，不是某个具体对象。

**属主登记用的必须是装饰前的底层指针**：store 会被包装（桥接、容量降级等），包装后的指针与真身不是同一个身份——按包装件登记会让同一份物理存储被认成两个属主，或让按指针查属主落空。因此登记与查表都以装饰前的那一份为准。

错误也必须形态统一：封路状态一律可用 `ErrResourcePoisoned` 检出，而**原始失败原因同时保留可匹配性**（经 `errors.Join` 包装，`errors.Is` 仍认得最初那个错，包括 `ErrReclaimUnconfirmed`）。调用方既能判断"这条路被封了"，也能判断"是因为什么被封"，两者不互相顶替。

<a id="engine-generation"></a>
## 九、引擎与后端同代拥有；构建失败降为仅容量

配置了引擎时，引擎与它的后端属于**同一代登记条目**：同一代内所有消费者共用同一个活引擎实例，单个借用者释放拆不掉它；最后一次释放把它一起关闭（连带回收它的后台工作协程）。重开（新一代）必须拿到**绑定新后端的全新引擎**，绝不复用绑到已关后端上的陈旧引擎。

引擎构建失败时**降级而非留下悬垂对象**：登记条目的引擎为 nil，后端照常发布并关闭；每个借用者仍得到**各自独立的容量钩子**、检索退化为关键词路径（不做向量索引）。新一代重开且提供方正常时，必须同时拿到新后端与新引擎——以此证明陈旧一代被完全隔离。

<a id="reverse-release"></a>
## 十、构建失败按获取逆序交还，登记先于可失败接线

每一次成功取得的运行时资源，都必须在**任何可能失败的后续接线之前**登记为可回收责任；只有构建成功完成交接才撤销登记。任何失败出口都不得遗漏已获资源的释放，也不得把释放押在一个晚于新可失败步骤的 defer 上。回退按**获取的逆序**进行，且"已登记尚未发布的部分"（包括构建到一半失败的那个父）也必须被撤销，不留半截属主。

<a id="composition-barrier"></a>
## 十一、组合根期间抬遗忘登记屏障，由顶层构建一次放尽

一次构建从**资源登记起**就在被触及的共享 store 上抬起**登记屏障**（`BeginHold`），直到本次构建（全部 agent 构造＋核对）返回才放下：屏障存续期间，生命周期扫描**无条件暂停遗忘遍次**，没有宽限逃逸。这条契约存在的理由是**登记间隙**——后到的共享 owner 不能因为"注册顺序恰好靠前"或"宽限计时还没走完"就被一次插缝的遗忘遍次吃掉材料。

- **按 store 聚合**：同一份 store 被多个 agent 触及只抬一层（构建内去重），不是每个 agent 一层；
- **无物可停就跳过**：没有保留租约（也就没有破坏性扫描）的 store 不实现这一面，调用方把"能力缺失"当作"无物可暂停"，**不是错误**；装饰链必须把这能力递归透传；
- **放尽押在顶层**：只有最外层构建负责释放，抬起的每一层在那一刻一起放下；per-bus 的 `Arm` hold 嵌套在这段窗口之内；
- **多余释放是 no-op**：屏障按引用计数，最外层归零才放闸；重复 `EndHold` 既不 panic 也不会反向放掉一个未配对的持有；
- **可重入**：后一次构建（热重载壳）在同一 store 上再抬一层，窗口按构建嵌套计数，不是"一次构建永久暂停遗忘"；
- 释放时先把持有集合摘清、再在锁外逐层放下，避免与扫描器唤醒互锁。

**屏障取代侥幸**：登记与核对之间的窗口只能靠这把屏障关住，**不能**靠注册顺序排在前头、也不能靠一段宽限计时——两者都会随并发时序偶然成立，偶然成立时材料就丢了，且丢在没人报错的地方。

**恢复保留的登记权只属于常驻属主的构建**：热重载的执行器壳借用同一份共享 store，但不得在它上再登记恢复保留（按收件箱武装保留、也不保护待处理原件）。壳自己的总线永不 ack、产物被直接丢弃，因此它登记的每一份持有都没有归还路径——租约**永久泄漏**；而登记失败的支路若留下一个没有配对放尽的抬起，**遗忘屏障就永远挂住**。判定只看构建形态（是否执行器壳），不看时序或计数：壳必须走易失总线、不开兜底落盘。

构造这类用例有两个硬前提：收件箱里必须放一份**超过保留期**的未 ack 原件，否则没有东西进入破坏性扫描，测不出泄漏；而要观察这份租约的持有数，必须在构建之前就经同一获取路径拿到那份共享实例——它是构建在进程内建立的，事后除了该实例本身无处可达。

## 已知缺口与演进方向

- 封路没有解封出口（第八节）：确认停止之后也不能恢复该路径，只能重启进程；未做在线解封，因为无法证明陈旧生产者已经退出。
- 同路径获取已由 per-key 互斥串行化，"竞争者抢先发布"那条丢弃分支在现行实现下不可达，保留为防御腿。
