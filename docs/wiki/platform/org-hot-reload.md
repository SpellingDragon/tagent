# 组织级热重载（配置换代、单一应用记录与无锁读面）

<a id="overview"></a>
## 一、机制定位

常驻入口 agent 的组织（拓扑＋参数）可以在不重启的前提下换掉。承担这件事的是**单一版本协调器**：它持有"已发布的组织代际"，并把配置变更分成两类处理。

| 变更类型 | 效果 | 是否前进结构代 |
|---|---|---|
| 结构变更（指纹变化） | 重建执行器与 agent 实例，整代原子替换 | 是 |
| 数值热参变更 | 只把新参数下发到各 agent 的真实对象，不重建 | 否 |

**为什么是"整代"而不是"逐个换执行器"**：一次配置可能同时改动拓扑与多个 agent 的参数。若逐个替换，读者会在中途看到半新半旧的组合；整代替换保证任何时刻读到的都是一个完整一致的代际（见第五节的无半提交约束）。

<a id="fingerprint"></a>
## 二、结构指纹的取舍准则

**只有"改了必须重建 agent 实例才能生效"的字段才参与指纹。** 这条准则决定了两侧清单：

**入口身份是这条准则的一个特例**：它被列入"参与指纹"，是为了让改名**被识别成一份需要重启的差异**，而不是为了把常驻入口换掉——入口 agent 带着会话、事件环与共享底座，热迁它等于在一次发布里搬运进程级身份。拒绝的时机与形态见机制清单（平台文档「配置热重载」按序门第 1 条），此处不重述。

- **参与**：入口 agent、prompt 目录、系统与工具声明、模型/推理参数、压缩配置、冥想配置、工作区与描述、以及**全局 model／provider**——子 agent 未显式指定模型时经 provider 注册表解析，所以全局默认值的变化确实会改变重建结果。provider 侧只取参与模型实例构建的字段（含 API 端点）。
- **不参与**：持久化路径类字段（治理、可靠性、各 agent 的记忆配置、MCP 服务器、进程级杂项，以及顶层 API 端点）。它们在运行时**无法迁移已有资源**，改了必须走重启——把它们放进指纹会造出"看起来热更成功、实际旧资源还在用"的假象。
- **不参与**：五个数值热参（压缩阈值、最大令牌、保留最近任务数、任务默认与终态 TTL）。它们已被改造成**消费方在安全边界读单条已提交记录**，因此改变它们不需要重建，由"指纹未变"分支走数值热应用。

规范化要求（否则指纹不可比较）：字段顺序固定（决定 JSON 键序）、map 按名排序、逐 agent 单独规范化 ⇒ 同一份语义配置在任何 YAML 迭代顺序下得到**逐字节相同**的输入。

同步义务：参与字段必须与配置结构体保持一致，由"覆盖检查"测试守住（新增相关字段而未纳入指纹会被测出）

同步义务是双向的：漏纳入会让该字段的变化不触发换代；反过来，白名单里若有一个结构体上并不存在的名字，死字段会继续参与指纹。两个方向都必须由"覆盖检查"这一个测试暴露，字段集合与结构体逐名对齐。

别名折叠（旧式扁平键折进统一的 ModelRef）必须在指纹之前完成，且**被折叠字段仍真实参与指纹**：只测"两种写法指纹相等"不构成证据——字段整体不进指纹时两种写法同样相等，真变更也一并隐身。折叠还必须是不动点：对已折叠的配置重跑既不搬值也不复活扁平键，否则指纹会随检查次数漂移。

折叠义务不止配置键：**运行对象别名同样必须归一**——`kind:` 省略与显式 `kind: agent` 是同一件事的两种拼写，可达性、退役与"仅远程声明"这类判定都同时接受它们；若归一被"简化"成只认显式值，同一份配置就会因拼写不同走出不同拓扑。

<a id="generations"></a>
**被测文本的换行必须来自解释型字符串**：用 raw literal 写匹配模式时 `
` 不是换行，替换静默不命中，"新增"就退化成只定义不可达的候选——拓扑没变、只有指纹变了，而测试照样绿。

**一个用例只允许一个 delta**：候选文本若同时改掉其他 agent 的存储段，被拒的原因就变成"存储变更须重启"而非被测的拓扑规则，断言看似通过、实际在验证另一条规则；构造形状时必须让其余 agent 的段落逐字节不变，只有目标 agent 发生变化。

**配置 map 的元素不可寻址**：改 `c.Agents["main"]` 的字段必须先取出副本、改完写回，直接下标赋值编译不过；因此这类审计用例普遍带一个就地修改的闭包。

**逐用例隔离必须走运行时同一个 Clone**：浅结构拷贝会共享 Tools 的底层数组与 Properties 的 map，一个用例就能改坏基座夹具，后序用例在污染数据上照常判绿。

## 三、版本簿记：序号、环与两个计数

| 量 | 含义 | 前进时机 |
|---|---|---|
| 结构代（generation） | 发布身份 | 结构发布与回滚；**回滚同样前进**，绝不重用旧序号 |
| 完整应用计数（revision） | 包含数值热应用在内的提交次数，仅供观测 | 任何一次完整成功应用 |
| ring-2 上一代 | 回滚数据源（配置与记录各一份） | 每次成功应用轮转 |

要点：**发布身份是序号，不是内容指纹**。回滚到同一内容仍产生新序号——否则"回滚后的这一代"与"上上代"在诊断里无法区分，回滚事件本身消失。结构代与完整应用计数是两个轴，不得用后者做路由依据。

<a id="apply-record"></a>
## 四、单一应用记录（谁是权威）

每代携带**逐 agent 的应用记录**：该 agent 本代生效的完整热参，加一个"本代是否仍路由它"的标志。它是热参读取方解析数值的**唯一真源**。

被移除（排水中）的条目携带该 agent **最后一次生效值**而不是默认值。理由：owner 一旦移除，任何按默认值重新参数化的行为都会凭空造出一份它从未有过的配置；保留末次生效值才让"存在但排水中"这一状态可被读者直接观察，无需第二次查询。

数值下发取**本代解析结果**，不做增量合并：定义里删掉的字段回落到解析默认，而不是停在上一次被热更成的值。例外只有排水条目（携带末次生效值），排水者就是本代不路由的 agent——仍被路由的照常收到新值。

**解析默认的归属**：这五个热参的默认值真源在**消费方**——压缩阈值与最大令牌、保留最近任务数来自 agent 层的解析默认，两个任务 TTL 来自 `agent/task` 的构造常量。装配侧为了输出"全量 desired"会把它们各复制一份兜底值，但**不得在此新增或修改默认**：默认属于消费方的解析规则，写在装配处就会造出第二真源（改了这里、消费者仍按自己的规则生效，诊断与生效值随即分叉）。

<a id="lockfree-read"></a>
## 五、读面无锁，且必须与代际同临界区整体轮转

记录的读面用原子指针发布，**只允许在三个提交点与 current 一起轮转**，且每次都是完整不可变快照。因此读者要么看到旧一代的完整记录、要么看到新一代的完整记录，**永远不会看到半次轮转**。

为什么必须无锁：压缩器会在每个存活上下文管理器的每个消费边界解析它的数值组。若这个读要走提交临界区的锁，就把提交路径放到了压缩读路径上——轻则争用，重则成环（提交期任何代码再去读一个 owner 的热视图即重入）。深拷贝是同一契约的另一半：重载路径会跨提交复用自己的切片，读者绝不能观察到一份正在被改写的切片。

<a id="rollback"></a>
## 六、回滚恢复结构也恢复数值

回滚＝把上一代**重新发布为新序号**，同时恢复结构与五个热参。环本身保持不变：连续回滚仍面向同一上一代（不会把回滚本身记成新基线）。

判"有没有东西可回滚"必须用**双轴同一性**：结构指纹相同**且**热参摘要相同。只看指纹会错判——一次纯数值应用后指纹没变但热参变了，此时应当可回滚。

**启动代就是回滚环上的第零代**：装配期播种的那一代带序号 `0`，其配置私有拷贝当场入环。环必须有这一格，否则第一次结构热更会把"上一代"写成空值，此后回滚永远只能说"无上一代快照"——用户改坏了配置却没有任何回到改动前的通路。

**回滚能力与首次更新的类型无关**：运维入口在装配期一次性接好，不取决于是否发生过结构发布。一次纯数值热更同样会把启动代轮进环里，若入口的接通被绑在结构发布分支上，就会出现"环里有数据、回滚却静默什么都不做"的组合——回滚入口必须读得到那格数据，与谁把它写进去无关。回滚闭包自身只按当前协调器的状态取快照，所以入口接通的时机不改变其行为。

<a id="identical-apply"></a>
## 七、语义完全相同的应用不轮转

纯数值热应用先比对热参摘要：完全相同则**不轮转环、不加计数、不动时间**并返回"未变更"。否则轮转、加计数、推进"最近应用时间"（不推进"最近发布时间"，因为结构没动）。

已知边界：仅"未设置"与"显式写了默认值"的差异会让摘要不同并触发一次轮转。这是无害的冗余（生效值相等），代价仅是一次多余计数。

<a id="diagnostics"></a>
## 八、有界诊断形状（成功与失败同一种可检查形式）

| 面 | 约束 | 为什么 |
|---|---|---|
| 代际状态 | 与提交同锁产生，一次读得到"已发布代＋两个时间＋最后一次失败＋本轮逐 agent 回执"的一致组合 | 避免拼出一个不存在的中间态 |
| 实时欠账 | 与状态**分开成组**，并携带自己的采集时刻 | 它是"此刻运行期引用计数"的读数，不是提交记录的原子快照；混在一起会被误读成一次成功快照 |
| 指纹与 desired | 只能当**不透明诊断标签**；任何执行路径不得据它选版 | 声明过：它们不是应用可见的身份 |
| `desired != fingerprint` | 正是运维要看的事实（"我改了，为什么没生效"）；解析或指纹失败时 desired 为空 | 分歧必须显式可见，而不是被静默收敛 |
| 逐 agent 回执 | 只保留最近一轮，整块替换，按拓扑限界，不累积历史 | 诊断不需要历史；累积等于另建一份状态存储 |
| 回执与应用记录 | 两者都按 agent 名字排序后交出 | 常驻表是无序集合，逐 agent 的遍历序随迭代随机化漂移；不排序时同一份配置两次诊断给出不同行序，读者无法逐项对比，机器比对也会把纯换序误报成变化 |
| 关闭状态 | 区分"已发起"与"资源已退出"两个事实 | 折叠两者会让一次**有界返回**被读成"退出已完成" |

回执只有两种真实结果：`applied`（属于本代可路由拓扑，参数已下发到它的真实对象）与 `draining`（本代不再路由它，因此**故意不碰**，数值字段为零，含义是"本轮未评估"而非"零配置"）。

回执的可诊断价值来自一个更强的要求：它报的数字必须在真实消费者处交叉验证——等于该 agent 当前 live compressor 实际消费的预算线与 keepRecent、等于其 TaskManager 实际解析的 TTL，而不是回显请求下发的那组数值，也不是"setter 被调用"的回声。判别按属主分离：每个 agent 对齐它自己的压缩器，两个 agent 必须取到可区分的值，否则共享一个全局消费者也能蒙过。没有回执槽的轴（如 terminal TTL）就在它被真实消费处证明。排水（`draining`）条目数值字段为零，其真实消费者保持末次生效值而非被重新默认。

<a id="config-clone"></a>
待决面必须**常驻呈现**：没有待退役项时交出**空列表**，而不是不建这个键。"键不存在"与"列表为空"是两件事——前者无法与"诊断面根本没接线"区分，会让一次接线缺失被读成"一切干净"。

## 九、配置快照的私有化

每个发布代**私有持有**自己那份完整配置的深拷贝：回滚环不得别名任何后续构建可能触碰的活 map，重发布出去的一代也不能观察到被记录之后才发生的编辑。

实现选择：经序列化往返做深拷贝，因为配置是纯数据且标签对称——将来新增嵌套字段会被自动拷贝，而逐字段手写拷贝会在第一个新增字段处腐烂。两处刻意偏离：进程级路径字段不参与序列化，需手工重贴；带 omitempty 的"空但非 nil"集合回来会变成 nil——这对配置解析是等价的（遍历、长度、下标同样处理），且指纹在同一规范化形上计算，故 desired/effective 比较不受影响。

<a id="candidate-refusal"></a>
## 十、被拒候选必须完全退场

候选被拒绝（无论来自热加还是回滚）时，它的每一份副作用都必须撤销：属主登记、常驻表项、存储 writer 槽一个都不留；发布序号不前进，在线拓扑与拒绝前完全一致，已在途的调用照常跑完。

跨多个新增顶层项的公共依赖只构建一次、共享同一属主：单写者语义使第二次获取必然失败关闭，因此"回滚确实把结构取回来了"本身就是这条规则的见证，无需额外的指纹断言。

**回退按获取逆序整体进行**：候选事务的失败处理是一个 defer 的整体放弃，撤销顺序与获取顺序相反，所以后段失败不会半改在线拓扑——未发布的属主不得留在在线清册，其存储租约也不得被持有。最近一次回退的名单对测试可观测，用来钉住这条逆序要求。

候选的构建遍历**按名字排序**（可达集合本身无序）：失败落在哪一个属主、回退时要撤销哪些已构建的部分，都由这个名字序决定。要构造"前段成功、后段失败"的候选，就用名字前缀控制顺序。

<a id="close-drain"></a>
## 十一、关闭必须覆盖排空期间落位的属主

组织关闭要覆盖所有属主、候选与共享资源。次序是关键：属主关闭器登记在停止重载之后——一次仍在进行中的构建可能在关闭器做完快照的瞬间又新增一个属主，若先登记关闭器，这个迟到的属主就永远躲过清扫。

因此排空期间落位的属主同样必须被恰好关闭一次，其存储租约真正归还；租约只在最后一步交出，绝不在未收敛时交。

多属主清扫**按名字排序**：常驻表是无序集合，不排序则关闭顺序与汇总后的错误文本都随迭代随机化漂移，同一次故障两次跑出不同输出——既无法复现，也没法把"哪个属主仍被持有"当作可依赖的诊断事实

**关闭一旦发起，热更与回滚一律拒绝**：懒检测与运维入口两条路在动手构建候选之前都要看停止位。向已经开始拆除的运行器宿主发布新一代，等于在收尾之后还在换入执行器并退役运行器——那会让一次本应有界返回的关闭变成无人收敛的状态。拒绝发生在构建之前，因此不产生任何需要回退的副作用；被拒时在线拓扑与关闭发起前完全一致。

**进程级共享资源的关闭器排在属主之后**：被多个属主借用的进程级资源（如 MCP 注册表）其关闭器必须**最后**登记，于是它在所有借用者退尽之后才被关闭；先登记它就会在借用者仍在运行时拆掉共享底座。同一个道理也规定"谁拥有关闭责任"：轨迹记录器的收尾由 agent 的 `closeOnce` 单主持有（在运行器停止之后 flush），因此它**不得再被登记为普通 closer**——双主会带来一次早于运行器停止的关闭。

<a id="owner-retirement"></a>
## 十二、属主退役：三段语义与持有必须可观察

移除一名成员意味着两件事：**停止接受新路由**，以及**其义务全部收敛后**关闭独占组件、释放存储租约并撤销属主登记。仍被路由的实例必须保持原样，不因别人的移除而改变身份。

同名成员的回退按三段判定：其属主**仍在排空**——复用那一个实例，另建属主等于给同一存储第二个 writer；其属主**已开始关闭**——在任何资源建立之前拒绝该候选，复用不可能、放入新的则构成同一存储身份的第二个 writer；其属主**最终退出**——按恢复协议新建属主，而不是继续拒绝。对前属主已彻底消失的名字持续拒绝，等于把拒绝门漏进准入路径。

在途义务对退役的阻断必须可观察：仍有在途执行的属主不被移除它的那次发布退役，提前关闭属于禁止情形。释放本身带着排空推进，因此不需要额外业务回合即可到达最终退出。名字反复增删的资源上界由**当前路由加真实待决义务**决定，绝不按出现过的名字数收敛。

**会话服务按同一条界线归属**：换代时只有入口 agent 的执行壳复用常驻会话服务（宿主的输出接线与同一个 session 的续写都挂在常驻实例上），子代理的壳一律自己新建。让子代理壳也复用入口那一份，它的用户消息会经入口的写入钩子流进宿主输出通道，并把记录污染进入口 session——这是「被多属主借用的共享状态」最容易被误扩的一处。

退役关闭的是属主**独占**的组件；被多个属主借用的共享后端不随任一属主退出而拆除——它等所有借用者退尽、存储租约恰好释放一次，过早或重复释放都会封住路径。菱形共享叶子在别一代仍有合法委派能力时不得退役：它自己没有待决义务，不代表可以被关。

**同名重入的门禁必须排在排水扫描之前**：本代想要的一个名字可能已在退役名单上、且其属主已开始关闭。此时复用不可能，放入新的等于给同一存储身份开第二个 writer，所以候选必须在任何资源建立之前被拒绝，在线拓扑保持原样。次序是这条规则能否成立的关键——若先做排水扫描，本次热更正要带回的那位属主会先被退役掉，门禁就永远没有机会触发。

**退役判定的输入只有"实际在任那一代"的可达集**：它在启动期取一次，此后只随结构发布与回滚重新求值。绝不拿"某个被拒候选对应的那份配置"来推断谁还在被路由——被拒的编辑没有生效，按它退役就会把在线拓扑仍在路由的属主关掉（第十节的完全退场与这一条是一对：候选的副作用要撤销干净，但它从未改变过路由事实）。

所有权面的可观察证据就是实例身份本身：断言比较的是 owner 与其 store 的指针——同一实例即复用，不同实例即被复制或替换；行为侧的真实路由由委派测给出，两侧各证一面，不得互相替代。

身份断言只覆盖所有权面，**不证明数据落点**：两台存储指针不同，并不能排除"把子 agent 的回合写进宿主存储"的实现同样全绿。热增的数据归属必须把数据流走到底——真实委派、宿主拿到真实返回、子回合记录只出现在子自己的存储里、落盘字节可寻、关闭后由其主人释放存储注册。区分归属的判据是**记录种类**，而不是"宿主侧检索不到那段文本"：委派返回本就作为宿主回合的一部分被记录，那是正确行为而非泄漏。

<a id="closed-owner-refusal"></a>
## 十三、已收敛属主的再进必须具名拒绝

一个属主完成收敛（排空、执行器关闭、属主登记撤销、离开常驻表）后，仍可能有陈旧持有者指向它——旧代工具表里泄漏的包装正是这种东西。它此刻发起的每一份工作都必须在共享闸门上被拒绝，且拒绝要能具名区分：

| 再进面 | 拒绝形态 | 不得出现的形状 |
|---|---|---|
| 获取执行器 | 交出的运行器为空 | 把已关闭的执行器交给新回合 |
| 输入接受 | 环路已终止的具名错误 | 静默收下无人处理的消息 |
| 启动工作 | 世代已关的具名错误 | 在已关闭执行器上跑完一回合 |

两条附加约束：被拒的入口不得在账面上留下新登记——排空已报告干净之后再登记一份引用，等于重开一个无人等待的义务；再进必须有界返回，闸门挂住比拒绝更糟，因为它把一个可诊断的失败变成一次超时。"关闭已发起"阶段的拒绝属于准入规则（第十二节），本节只管收敛完成之后。

<a id="trigger-timing"></a>
**撤销登记的权力只属于登记它的那个属主**，而且必须在它自己的存储退场真被取走之后才做（由那一次收敛触发）。热更换代的执行壳借的是常驻属主的存储，它**绝不撤销**常驻那份登记——一旦撤掉，真属主仍在服务，分区却已对第二个写者开放。

## 十四、触发时机：检测不等待构建，构建不封住业务

配置检查在业务获取时懒触发，同步检查由运维驱动，两条路共享同一条互不阻塞约束：业务获取永不触碰重载互斥量，因此无论构建是否停在屏障上，它都立即拿到当前生效的那一代。

| 路径 | 等待什么 | 绝不做什么 |
|---|---|---|
| 懒检测（业务回合内） | 不等候选构建 | 不让见证编辑的回合为新代等待，也不在构建期间发布 |
| 手动同步检测（运维） | 等整次构建与发布完成 | 不封住并发业务的获取，业务仍拿旧 effective |
| 关闭排空（Close） | 等重载互斥量到手后走完拆除 | 不封住并发业务的获取，也不无界滞留 |

代际切换只对发布之后启动的回合可见，发布之前启动的回合继续用旧的一代——这是整代原子替换落在读面上的形状。这批断言必须配一个对照组：一个真正持有重载互斥量的操作要被屏障挡住，否则"不阻塞"可能只是因为构建根本没跑。

**一次读取故障不改变生效面**：配置路径消失或不可读时，检测直接返回，什么都不做——既不把拓扑清空，也不登记失败为"已应用"。热更通路只在读到的内容与当前生效面确有差异时才动手；文件系统的一次抖动不构成配置意图。

**该对照组所用的屏障由测试注入**，生产恒为空，因而恒为零成本。

**同一个时刻只允许一趟后台重建**：懒检测发现 mtime 变化后以单飞标志抢占，抢不到的请求直接返回——多余请求被合并而不是排队；处理完成的标志是记下的 mtime，同一次修改被反复 stat 到不会重复触发（重复检测因此是无操作）。这条合并与上面的"不阻塞"是两半：一个保证不排队堆积，一个保证业务不等待。

<a id="staged-add-visibility"></a>
**成本快慢不能证明并发语义**：整次热更的均值耗时（即使再加单次上限）只说明这批构建碰巧快，既不保证构建真的停在短锁之下，也不保证业务获取路径不碰那把锁——负载抖动或更快的机器都能让一个会阻塞的实现暂时通过耗时门。所以耗时读数只作观测样本；短锁合同要由**结构性证明**承担：把构建停在持锁点上，同时观察业务获取能否照常通过（获取方被挡到超时即属违约）。以耗时阈值充当正确性门，是本项目明确拒绝的形态。

## 十五、暂存新增只在唯一提交点变得可见

候选的新增属主在构建期间只活在**候选私有 overlay**（`candidateOverlay.added`），并入常驻表由 `commit()` 在调用方的提交临界区内一次完成——那是新增属主对并发读者唯一的可见点。提交之前：`ResidentTable()` 取不到它，任何已发布执行面不 offer 它，`OrgDiagnostics` 的发布序号不前进。提交之后：三者同时成立，序号恰好推进一个。

判据必须在提交临界区内停车观察才有效。只在提交完成后断言"新增可见"，对"构建在途时不得出现半提交拓扑"这一半是空洞的：父面已接好而子属主尚未合并，正是这里要拦的形状。

"不可见"有一条刻意的边界：新增属主的存储属主登记与逐 owner memory 指纹在构建期就被取得，`StoreOwnerSnapshot()` 从那一刻起看得见它。被拒候选的回退必须撤销本候选登记过的每一个属主，包括构建到一半失败的父；把登记也说成提交前不可见，描述的就是另一种设计。


<a id="memory-preflight"></a>
新增属主的**描述与记录**也必须在那同一个提交点接上：诊断收据集与记录源（`HotSnapshot`）都不得晚于候选并入才反映它。若记录源在候选合并之前就已取好，新属主在这次发布里两处都查不到，要等到下一次数值变更才被补上——那就不是"发布即一致"，而是延迟生效。

## 十六、存储配置的变更判定：独立于指纹、限定判定域、基准带粘性

持久化路径类字段改了必须重启（第二节），但它们**参与不了**指纹判断的那条通路——指纹没变时结构分支根本不会走。所以存储段的变更有一套自己的判定，三条约束缺一不可。

| 约束 | 内容 | 破坏后的形状 |
|---|---|---|
| 判定位置 | 逐 agent 比对存储段，发生在组织指纹比对**之前**，命中即拒绝并明示须重启 | 挂在指纹变化分支里，则"只改存储段"这次编辑永远走数值分支，静默生效成一份没人确认过的存储配置 |
| 判定域 | 只对**已有属主且本代可达**的名字判定 | 判定域放进"定义仍在但已被摘路由"的名字：拒绝它防不到任何第二 writer（本代不会构造它），却永久冻结整条热更通路；判定域放进全新 agent：它自带存储段不构成运行时存储迁移——路径与已有 agent 相同时由获取环节共用同一实例并受进程标识冲突校验保护，误拒它等于让热新增永不可达 |
| 基准粘性 | 基准只在启动播种与真正新增时前进；已被摘路由的已有名字不收敛基准 | 基准随摘路由收敛，则同一份未生效配置改完别的字段就以"新基准"通过，存储段的变更被绕开 |

同名重入会让该名字回到判定域，旧基准仍然作数：同一份从未生效的配置无论再改哪个字段，都继续按生效面拒绝，直到真正重启。

<a id="percall-overrides"></a>
## 十七、per-call 覆盖层：视图替换只活在一次调用里

空白委派 agent 的定义留在文件里，动态性全在调用参数上：一次委派可以换掉**本次调用**的系统提示词、模型引用与工具面，三件都只作用于那一次装配，随调用结束失效。

| 参数 | 作用 | 上界 |
|---|---|---|
| `system_prompt_override` | 替换本次调用的系统提示词 | 与文件提示词同信任级，调用方已是 agent 自身 |
| `model_override` | 换成本次调用服务的模型 | 必须是已注册引用，未注册即拒绝 |
| `tools_subset` | 收窄本次调用可用的工具面 | 只能是该 agent 声明清单的子集，越域即拒绝 |
| `context_refs` | 把指定事件的正文作为上下文交给本次调用 | 走既有的外部上下文通道，不另建传递面 |

三条形状缺一不可：

- **装配期一次定稿**。覆盖在 `Run` 的本地装配处读一次、压进本次调用的配置副本，之后该视图不回读任何共享态。提示词文件源的每轮重写通路对本次调用必须关掉——覆盖拥有本次调用的提示词，否则"替换"会被下一次回调冲掉。
- **结构性防泄漏**。覆盖只存在于 invocation 结构内（与 `RuntimeState` 里的外部上下文同族），没有 owner 级或进程级的可写槽位，因此紧随的、不带覆盖的调用必然回到本代定义。越域与未注册引用在**参数校验点**具名拒绝：错误里点名被拒字段与越域条目，拒绝先于任何执行与记账。
- **冻结与重放**。覆盖随 `Declarative.Overrides` 进 `task_spawned` 事实，登记重建折叠时逐字段还原；标量 knob 仍留在 `Declarative.Params`，视图面与参数面不混成一个袋子。

### 空白委派 agent 的 org 条目

工具清单就是它的最大工具域（条目引用全局注册表，不复制工具实现）：

```yaml
agents:
  - name: temporary-worker
    description: 空白委派 agent：定义在文件里，动态性在调用参数上
    system_prompt:
      files: [prompts/shell.md]
    tools:
      - {kind: tool, id: read_file}
      - {kind: tool, id: save_file}
```

一次带覆盖的委派调用长这样：

```json
{"request": "只读地把这份报告的结论摘出来",
 "system_prompt_override": "你是摘要器，只输出结论文段，不得提议后续动作。",
 "tools_subset": ["read_file"],
 "context_refs": ["evt_01f3a7c2b8d94e10"]}
```

`tools_subset` 越出清单（例如请求 `mcp_call`）得到的是具名拒绝，而不是"悄悄少给几个工具"；模型引用没注册同样具名拒绝。省略全部覆盖即等于使用当前生效代的定义。

## 已知缺口与演进方向
- 短锁合同已有结构性证明载体：`buildPark` 把候选构建停在持有重载互斥量的位置上，业务获取照常通过才判绿；耗时样本仅作观测。
- 结构代与完整应用计数并存，但只有前者参与语义；后者若被任何路由读取即违反本文第八节，尚无静态检查阻止这种读取。
- "未设置 vs 显式默认值"会触发一次冗余轮转（第七节），未做规范化以消除该噪声。
- per-call 覆盖的跨重启重投只做到登记重建这一层：`Declarative.Overrides` 已随事实链还原，而重投入口（`SubagentRedispatcher`→`RedispatchAsync` 只带 request 正文）尚未把还原出来的覆盖压回新调用，故进程内重放逐位一致、跨重启重投暂按无覆盖执行。补齐点在委派重投递的构造侧。
