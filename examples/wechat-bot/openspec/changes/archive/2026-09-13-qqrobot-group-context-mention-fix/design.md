# 群聊上下文保真 + 出站真提及修复 · 技术设计

## Context

- 入站消息在 service/gate 下某渲染点被加工为历史快照后送模型；加工过程剥掉了 `<@openid>` 提及标记、把图片/GIF 消息渲染为空行。
- 出站回复走 robot.go 发送路径，模型输出的 `@显示名` 以纯文本发出，QQ 官方真提及要求 `<@member_openid>` 形态。
- persona 提示词无指代消解约束规则。
- 机器人自身回复是否进历史未核实——用户反馈"回复很奇怪"（20:51 @NANA 答豆包榜单、20:53 @Misaki 答非所问）疑与此相关。
- 20:51 时 G411 的提问是否被历史 char cap 裁掉待实证。
- **已取证（2026-09-13）**：未被裁掉。证据 robot.log.20260912_210001.gz 内 20:51:08 SetChatHistory 行含完整快照 48 条时间戳行，其中 [20:39] G411 提问行（簧图来源询问）完整在史（字节偏移 2230-2380 区域）。→ F4 缓解无需实施；20:51 @NANA 误判根因确认为提及剥除+图片归属丢失（F1 已修），非历史裁剪。


工程约束（硬性，来自调用方）：

1. CRLF 文件一律行级手术（`splitlines(keepends=True)` + 行内子串定位），多行锚前先实证行尾字节形态——本项目历史 3 连坑。
2. config.yaml 不入库（.gitignore），键位改动只落本机，代码内默认值为仓库权威。
3. go test 全绿才准 build；build 后 restart.sh 上线；验收 = 单实例 + 运行中 exe md5 = 盘上新件 + 心跳正常。
4. 提交推送 main；全程读回验证，不凭 success 回执断言落地。

## Goals / Non-Goals

**Goals:**

- F1：入站历史快照保真（提及 → 显示名、媒体 → 占位符、机器人自回复入史核实）
- F2：出站 `@显示名` → `<@openid>` 真提及替换
- F3：persona 指代消解软规则
- F4：历史 char cap 裁剪关键线索的缓解（视取证结论）
- 查清"回复很奇怪"疑云的根因线（自回复缺失 / char cap 裁剪 / 两者叠加）

**Non-Goals:**

- 不改 QQ 官方 API 协议层、不做主动 @（仅在模型自然输出 @ 时转换形态）
- 不做历史快照持久化格式重构（只改渲染层，不动存储层）
- 不优化模型提示词的对话策略（F3 只加指代消解约束，不改人格设定）
- 不做频道（guild/channel）私聊链路的同类改造（只动群聊）

## Decisions

### D1 提及映射数据源：窗口帧关联 + profile 注册表双源，未命中回退 `@成员`

- **选择**：显示名解析走两源优先级（同窗口帧 username↔openid 关联 → profile 注册表 → 回退 `@成员`）；出站反查走同样两源。
- **理由**：窗口帧关联是当次会话内最新鲜的映射（成员改名后仍准），profile 注册表覆盖窗口外成员；两源兜底比单源查全率高。回退 `@成员` 保证不残留 `<@...>` 裸标记（裸标记对模型是噪音）。
- **备选**：仅用 profile 注册表——被否，成员改名后窗口内映射会过期；仅用窗口帧——被否，冷启动窗口查不到人。
- **风险**：同显示名多人（重名）时窗口帧关联可能歧义 → 首个匹配即用，出站未命中保留原文的规则兜住不炸。

### D2 媒体占位符：`[图片]` / `[GIF]` 短占位

- **选择**：统一短占位符，不尝试描述图片内容。
- **理由**：渲染层无视觉能力，编造描述比不描述更糟（模型会拿假描述做推理）；短占位保住"此处有媒体"的事实，配合 F3 规则让模型自己说"没看到图的具体内容"。
- **备选**：接入图片理解模型生成描述——被否，超出本次修复范围（见 Non-Goals），且引入新依赖。

### D3 出站替换在发送路径单点完成，正则仅匹配 `@` + 显示名边界

- **选择**：robot.go 发送前对文本做 `@显示名` 反查替换，替换逻辑收敛在发送路径单一位置。
- **理由**：模型输出形态不可控（可能带空格/标点变体），在发送路径单点替换可覆盖所有出口；入站方向不做出站替换（职责分离，避免双写打架）。
- **备选**：让模型直接输出 `<@openid>`——被否，模型不知道 openid，且提示词约束会挤压本已有限的指令预算。
- **注意**：显示名含正则特殊字符时必须转义（Go regexp.QuoteMeta 或逐字匹配），否则 `@G411（备注）` 类名字会匹配失败。

### D4 机器人自回复入史与"回复很奇怪"疑云合并取证

- **选择**：把"机器人回复是否进历史"与"回复很奇怪"疑云合并为同一条取证线：若自回复缺失，则 20:51/20:53 的答非所问可解释为模型看不到自己刚说过什么（重复/错位）；若自回复在史，则疑云另查（如 char cap）。
- **理由**：三个症状（空行历史、假 @、答非所问）共享同一条上下文链路，合并取证避免重复读日志；根因若在历史快照层，F1 修复顺带缓解疑云。
- **备选**：疑云单独开线——被否，与 F1 取证重叠度高，单独开线浪费一轮日志分析。

### D5 F4 char cap 缓解：视取证结论决定做不做、怎么做

- **选择**：F4 不预先设计具体方案。先取证 20:51 G411 提问是否真被 char cap 裁掉；若属实再定缓解（如提高 cap 默认值 / 关键消息保底不裁 / 提及所在行豁免）。
- **理由**：调用方原话"视取证结论"——在没有实证前预设方案可能做无用功（也许 G411 那句根本没被裁，是别的原因）。
- **备选**：直接提高 char cap——被否，盲改可能引发 OOM/成本上升等次生问题，且不保证对症。

### D6 全程行级手术与读回验证

- **选择**：所有代码/配置编辑采用行级手术（`splitlines(keepends=True)` + 行内子串定位），多行锚前先 `hexdump`/字节级实证行尾形态（CRLF vs LF）；每步编辑后读回比对。
- **理由**：调用方明示"本项目历史 3 连坑"——CRLF 误判导致的多行替换错位是已复现过的失败模式；读回验证是"不凭 success 回执断言落地"的落实。
- **备选**：常规整文件替换——被否，风险已被历史证明。

## Risks / Trade-offs

- [风险] 历史快照格式变更影响所有群聊会话（老快照用旧格式渲染）→ 缓解：只改渲染层不改存储层（D 决策见 Non-Goals），老快照按新规则重新渲染无兼容问题（渲染是即时行为）。
- [风险] 出站替换误伤非提及的 `@` 文本（如 "@ 是 at 符号"的讨论）→ 缓解：正则边界收紧（@ 后必须紧跟已知显示名全集，且替换仅限提及片段 D3）；QA 用例覆盖"讨论 @ 符号本身"场景。
- [风险] persona 规则与既有提示词冲突/挤压 → 缓解：persona 写入前先读回全文，规则以"增补段"落点，不改动既有段落语义。
- [风险] F4 若取证发现 cap 裁剪属实的缓解方案影响 token 成本 → 缓解：缓解方案在取证结论出来后单独评估，不与 F1-F3 捆绑上线。
- [风险] restart.sh 重启失败/新 exe 未生效 → 缓解：验收清单硬性要求单实例 + 运行中 exe md5 = 盘上新件 + 心跳正常，任一不满足即回滚。
- [风险] CRLF 行尾形态误判再次踩坑 → 缓解：多行锚前逐文件实证行尾字节形态，行级手术工具化（一段可复用的行级手术脚本/函数）。

5. 提交推送 main，读回远端确认。
